# Security review, 2026-10-09: issue-run write-back, the tenant switcher, the provisioner's RBAC

Lane SEC-REVIEW, part of the security pass #476, which the owner un-deferred on
2026-10-09. Three changes merged on their lane review alone; each is a box in
#476's comments, and each gets a section below: who the attacker is, the path
they would take, the code that decides it, and the verdict.

Severity words: a **blocker** is a path that breaks a guarantee this platform
exists to keep (tenant isolation, the other team's resources, capacity,
fencing, secrets) and is fixed in this change, with a test. A **major** is a
real weakening that needs a precondition the platform does not hand an
attacker; it is described here precisely enough to be someone else's lane. A
**minor** is recorded and nothing more.

Line numbers are as of this branch (base `5440ea8`).

## 1. Issue-run GitHub write-back and the tick that submits as the run's creator (#545)

Box: #476 comment 5976542791. Code: `apps/swarm-api/swarm_api/issueruns.py`,
`issuecomments.py`, `issuesync.py`, `issueci.py`, `forge.py`, `forgewrite.py`,
`issuesweep.py`; routes `routes/runs.py` and `POST /v1/admin/runs/advance`
(`routes/admin.py:843`) and `POST /v1/admin/issues/sweep`.

### Attackers considered

* **A1, an outsider on GitHub**: anyone who can open an issue, comment, or open
  a pull request on a public repository a tenant has registered. Holds no
  SwarmCloud identity.
* **A2, a former member**: removed from the tenant's group after creating a run
  (or after being named `issue_sweep.submit_as`).
* **A3, a current member** of a tenant, pointing a run somewhere unexpected.

### 1.1 Can issue text reach a command or a credential? -- BLOCKER, fixed

**Path (A1).** The issue sweeper (`issuesweep.sweep_tenant`) lists every open
issue of every registered repository with the tenant's forge token and starts a
run for each one no skip rule removes. Before this change no rule looked at who
opened the issue: `skip_reason` checked labels, the exclusion list, a live run,
a claiming pull request and an unchanged issue, nothing else. Every swept run
is created `plan_approval: auto`, `auto_merge: true`, `fix_rounds: 2`
(`issuesweep.py:98-100`). So, with the sweep switched on for a tenant whose
registered repository is public:

1. A1 opens an issue whose text asks for a change -- or instructs the agent.
2. The sweep starts a run for it (`start_run`, submitted as `submit_as`).
3. The planner reads A1's text (the worker fetches the issue into the
   workspace, `agent_worker/issue.py`), and its plan is auto-approved by the
   tick (`routes/runs.py:410`, `by=AUTO_APPROVER`): no person reads it.
4. Build agents run with the tenant's `-git` token and provider keys in their
   container, push a branch, and the merge step merges the pull request once
   CI is green.

The planner's NOT_READY verdict and the review step are both an agent reading
A1's own text; neither is a gate against that text. The outcome is A1's words
turned into a merged change on the tenant's default branch, and an agent run
holding the tenant's credentials steered by A1, with no SwarmCloud member having
looked. That is the "issue text reaches a credential" question answered yes.

**Fix (this change).** `forge.SweepIssue` now carries GitHub's
`author_association` (`forge.py`, `sweep_listing`), and `skip_reason` refuses,
before every other rule and before any Firestore read, any issue whose author
is not `OWNER`, `MEMBER` or `COLLABORATOR` (`issuesweep.TRUSTED_AUTHORS`,
`issuesweep.py:118`, rule at `:308`). `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`,
`FIRST_TIMER`, `MANNEQUIN`, `NONE`, and an association GitHub did not send are
skipped as `author: <association>` (`author: unknown`). A person can still
start a run for such an issue from the console, where they see the plan.
docs/issue-runs.md's skip table carries the new row.

Tests (`tests/unit/control_plane/test_issue_sweep.py`):
`test_an_issue_an_outsider_opened_is_skipped` (six associations),
`test_an_issue_an_owner_member_or_collaborator_opened_is_a_candidate` (the
control), `test_the_author_rule_comes_before_every_rule_that_reads_firestore`,
`test_an_outsiders_issue_is_never_planned_written_to_or_run` (through the
route: no run document for the outsider's issues, the trusted one started), and
`test_the_sweep_listing_carries_each_issues_author_association` (the real
`GitHubIssues` reader, a missing field read as `""`).

Invariants: the sweep starts fewer runs and creates no demand of its own
(invariant 1 unchanged); nothing here touches tenant resolution (invariant 9
unchanged; the rule narrows what runs under it).

### 1.2 Outsider COMMENTS still reach the agents of a swept run -- MAJOR, not fixed here

**Path (A1).** The fix above trusts the issue's author. The worker's issue
fetch still renders **every** comment on the issue into the file the planner
and every build step read (`agent_worker/issue.py:388-403`: `Comment(author=
_login(...), body=...)`, no association recorded). A1 comments on a member's
issue on a public repository; the sweep's `_changed_since` sees the edit and
plans the issue again, auto-approved and auto-merged, with A1's comment in the
planner's input. A comment posted while a run is in flight reaches every later
step's fetch too.

The precondition the blocker did not need: A1 needs a member's open issue to
attach to, and the text arrives as a comment beneath the member's request.
Still, in a fully automatic run it is the same class of path.

**Fix, precisely** (out of this lane's territory: `apps/agent-worker/`):

1. `agent_worker/issue.py` `fetch_issue`: keep `row["author_association"]` on
   each `Comment` and on the `Issue`.
2. `render`: for a comment whose association is not `OWNER`/`MEMBER`/
   `COLLABORATOR`, write a line saying a comment by `<login>` (association
   `<x>`) was withheld, never its body -- for every task whose metadata carries
   `issue_run` (the run's planner, steps, fix rounds). Withheld, not fenced: a
   fence is an instruction to the same agent the text is trying to steer.
3. A test in `tests/unit/worker/` beside the existing issue-file tests, with a
   `NONE` comment withheld and a `MEMBER` comment kept.

Until then: do not switch the sweep on (`issue_sweep.enabled`) for a tenant
whose registered repositories are public. Both switches ship off.

### 1.3 Can a run write to a repository or issue its creator could not? -- by design; minor

**Path (A3).** `POST /v1/runs` takes any `owner/repo#N` that passes
`validation.parse_issue_ref` (owner and repo by pattern, github.com only) and
reads it, plans it, and writes comments on it with the **tenant's** token
(`routes/runs.py:566` `read_open_work`, `issuesync.sync_issue`). The creator's
own GitHub permissions are never consulted, so a member can make the tenant's
token comment on any issue that token can comment on -- for a classic PAT
with `public_repo`, any public issue on GitHub.

This is not a new grant: any member can already submit an ordinary task whose
`repository_url` is any repository the token can push to. The trust boundary in
this platform is the tenant, and the `-git` token is the tenant's capability,
held by every member (invariant 9); docs/multi-tenancy.md records the owner's
2026-10-01 decision that the write-back uses it "so that a tenant can only ever
write where its own token can". What bounds it is therefore what the operator
stores: a fine-grained PAT or a GitHub App installation limited to the tenant's
repositories makes "any public issue" impossible; a classic `repo` token, which
that doc says carries every permission the run needs, does not. Recommendation
(minor, docs only): say so in docs/multi-tenancy.md's permission table.

What the write path does keep, verified:

* **The token never leaves for another host.** Every URL is built from
  `GITHUB_API_HOST` and checked again in the transport (`forge.is_pinned_host`,
  `forge.py:273`); redirects are never followed (`_OPENER`, `forge.py:270`);
  the Actions-log redirect is fetched with no `Authorization` header and only
  on an allow-listed log host (`forgewrite._urllib_fetch`).
* **The pull request edited is on the run's own repository.**
  `issuesync.sync_pull_request` reads and edits `run.issue`'s repository at the
  number the integrator's `result_summary.git.pull_request` recorded
  (`issueci._opened_pull`, `issueci.py:335`; `issuesync.py:309`). A number,
  never a URL, selects it.
* **The merge is pinned.** `issueci.merge_target_unbound` refuses a pushing task
  that is not the run's integrator or one of its own fix rounds, and the worker
  checks the head it pins against GitHub.
* **A marker in someone else's comment is not ours.** `find_comment` matches only
  a body that begins with the marker and, once a write has reported its login,
  only that author (`forgewrite.py:393-425`).
* **Comment bodies are neutralised.** Every agent- or issue-authored field goes
  through `issuecomments.neutral` (`issuecomments.py:137`): redaction with the
  token as a known literal, `<`/`>` escaped, mentions broken, closing keywords
  turned into `refs`.

**Minor (recorded, not fixed):** `neutral` does not neutralise Markdown link and
image syntax. A plan that writes `![x](https://host/pixel)` posts an image
GitHub's camo proxy fetches, and `[text](url)` posts a link, under the tenant's
name. Escaping `[` `]` (or `!` before `[`) in `neutral` would close it; it is
cosmetic beside 1.1 and 1.2, since the agent's text is already the tenant's
comment.

### 1.4 Can the tick submit as someone who is no longer a member? -- no

Every submission the tick can make re-asks the directory first:

* **Auto approval**: `_advance_state` calls `run_owner_auth`
  (`routes/runs.py:410`), which calls `Authenticator.is_tenant_member`
  (`routes/runs.py:283`, `auth.py:676`) and raises `RunOwnerNotMember`; the run
  FAILS and nothing is submitted.
* **CI fix round** and **merge**: `issueci._start_round` and `issueci._merge`
  resolve `owner = owner_auth(ctx, run)` before claiming the round
  (`issueci.py:857`, `:1106`).
* **Sweep**: `routes.admin.sweep_submitter_auth` checks `submit_as` on every
  submission (`routes/admin.py:982`), and a swept run keeps that member as
  `on_behalf_of`, so the three above check them again.
* **A lookup that fails** raises `UpstreamUnavailable` (`auth.py:693-699`):
  the run waits for the next tick, never a guess either way.
* **What the context carries**: `is_admin=False`, no member scope, the STORED
  `tenant_principal` (`routes/runs.py:292-306`), so `tenant_for`'s collision and
  disabled checks run against the tenant as registered.
* **The tick's own identity** is admitted to `POST /v1/admin/runs/advance` and
  nowhere else on the tenant surface (`auth.ROLLUP_SWEEPER_ROUTES`), and it
  names the tenant explicitly; `advance_run` refuses a run of another tenant.

Covered by `test_a_creator_removed_from_the_tenant_fails_the_run_instead_of_a_fix_round`
(`tests/unit/control_plane/test_issue_run_ci.py:759`) and the sweep's
`test_membership_is_rechecked_on_every_submission`.

Residual (minor): the write-back itself -- the status comment saying the run
failed -- still uses the tenant token after the creator left. It writes about
the tenant's own run and submits nothing; that is intended.

**Verdict, item 1:** one blocker (1.1) fixed with tests; one major (1.2)
described for the worker lane; 1.3 by design plus a minor; 1.4 holds.

## 2. The tenant switcher's API half (#447, #617)

Box: #476 comment 5990263413. Code: `apps/swarm-api/swarm_api/auth.py`
`Authenticator._tenant_choices` (`:702`), `_select_tenant` (`:725`),
`deps.current_auth` (`deps.py:259-345`), `routes/tenants.py` `get_mine` (`:55`).

### Attacker

A3 again: an authenticated caller who sends `X-Swarm-Tenant: <other>` (or
`?tenant=` on the two browser-fetched routes) hoping to act in, or learn about,
a tenant they are not in.

### 2.1 Can a caller select a tenant they are not a member of? -- no

* The header is applied **after** the identity is verified and its memberships
  resolved (`Authenticator.authenticate` calls `_select_tenant` on the result
  of `_authenticate`), and it can only pick from `ctx.tenant_choices`
  (`auth.py:747-760`). Anything else -- another group's tenant, a personal
  `u-` tenant (the caller's own included), an admin group, a tenant that does
  not exist -- raises `TenantNotMember` before any route body runs.
* `tenant_choices` comes from `member_groups`, which holds only memberships
  Cloud Identity **confirmed** on this request (`auth.py:573-587`; a failed
  lookup that could change the answer is a 503, never a dropped group), filtered
  to the registered `tenant_groups` (`auth.py:719-723`). An admin group that is
  not a registered tenant group is never a choice.
* `tenant_id` and `tenant_principal` are replaced together from one entry
  (`auth.py:751`), so `Store.assert_tenant_scope`'s collision check (two groups
  whose local parts slug to the same id) keeps working; and `_tenant_choices`
  keeps only the first group per id (`setdefault`), the one the default rule
  would pick.
* The two early returns in `_from_claims` (a listed service account, the rollup
  sweeper) build an `AuthContext` with no `tenant_choices`, so any header from
  them is a 403.
* `?tenant=` is read only on `TENANT_QUERY_ROUTES` (`deps.py:306-310`), goes
  through the same `_select_tenant`, and a header and a query that disagree are
  refused after authentication (`deps.py:313`, `:328-331`).

Covered by `tests/unit/control_plane/test_tenant_switcher.py`.

### 2.2 Can a caller learn which tenants exist? -- no

* `GET /v1/tenants/mine` returns exactly `auth.tenant_choices`: the caller's
  own confirmed memberships, nothing read from Firestore.
* The refusal is one constant sentence whatever was named
  (`auth.py:756-760`), never echoes the value, and is raised before any read --
  so "not yours" and "no such tenant" are indistinguishable, in body and in
  timing (no lookup depends on the value). The value is not logged
  (`auth.py:755`).

**Verdict, item 2:** no blocker, no major. The header selects; it never grants.

## 3. The workspace provisioner's ClusterRole and its admission policy

Box: #476 comment 6064471463. Code: `kubernetes/rbac/provisioner-rbac.yaml`
(ClusterRole `swarm-workspace-deployer`), `kubernetes/policies/
workspace-provisioner-scope.yaml` (four ValidatingAdmissionPolicies),
`kubernetes/render.py` `POLICY_FILES`, `kubernetes/apply.sh --policies`.

### Attackers

* **A4, a tenant (a person with a workspace)** who wants the deployer's power.
* **A5, a holder of the deployer identity** -- what the policy must contain if
  the identity is ever used by something other than its one build.

### 3.1 Can a tenant reach the provisioner's service account? -- no

`swarm-workspace-deployer` has no key and no WIF binding, its own IAM policy is
written authoritatively empty, and the only thing that runs as it is the Cloud
Build trigger `swarm-workspace-apply`, which builds `refs/heads/main` only and
reads its build file from main (terraform/bootstrap/workspace_deployer.tf,
header items 1-3). The trigger takes two fields from a Pub/Sub message only
swarm-api publishes, after an admin approves (`_WORKSPACE_ID`, `_MODE`), and
passes them through `env`, never pasted into shell text
(scripts/cloudbuild/workspace-apply.yaml header). A tenant chooses none of what
the job renders.

### 3.2 Does the policy close every path to a cluster-wide grant? -- yes

* **Cluster-scoped writes.** The scope policy's `target` is `request.name` for
  a Namespace and `request.namespace` otherwise; it must match
  `^swarm-tenant-u-…$`. A cluster-scoped object other than a Namespace has no
  namespace, so `target` is `''` and is refused. RBAC grants no ClusterRole or
  ClusterRoleBinding write anyway.
* **`escalate` on Roles** lets the deployer write rules it does not hold; the
  roles policy requires every Role it writes to be one of three names with
  rules **exactly** the render's, in order, and no `resourceNames` or
  `nonResourceURLs`. A rule missing a field is an evaluation error, and so a
  refusal.
* **`bind`** is limited by `resourceNames` to the three Roles, and the
  rolebindings policy requires `roleRef.kind == 'Role'` (never a ClusterRole),
  binds `swarm-worker` (which grants nothing) only to ServiceAccounts of its own
  namespace, and binds `swarm-dispatcher`/`swarm-reaper` only to the scheduler's
  and the reconciler's two spellings. The deployer cannot bind Job creation to
  itself.
* **Verbs.** CREATE and UPDATE only; no subresource (so no `namespaces/finalize`,
  no `status`); RBAC grants no delete, no list/watch, and nothing on Secrets,
  Pods, Jobs or workloads.
* **Matching.** `matchConditions` select both spellings of the deployer (email
  and uniqueId), the same two subjects the RBAC binds; a parity test holds the
  lists equal (`tests/unit/worker/test_workspace_provisioner_scope.py`). No
  `namespaceSelector`, so an unlabelled namespace is no escape.
* **Fails closed at request time.** `failurePolicy: Fail` on all four; a CEL
  error or an unreachable policy refuses the write.

### 3.3 Does it close every path to another namespace? -- yes, with one naming caveat

Every namespaced write must be inside a namespace matching
`swarm-tenant-u-*`; `swarm-system`, `kube-system`, a group tenant's namespace
and the other team's cluster (`agents-staging`, a different cluster, which RBAC
here cannot reach) are all outside it.

**Minor:** the pattern is a naming convention, not an ownership check. A
**group** tenant whose group's local part slugs to `u-…` (a group named
`u-team@…`) would get the namespace `swarm-tenant-u-team`, inside the
deployer's scope. Refusing a `u-` prefix when an admin registers a tenant group
(`tenant_groups`, or the group-registration route) would close it.

### 3.4 Majors: what the policy does NOT pin

**3.4a The apply is not atomic, so the RBAC can land without its policy -- MAJOR.**
`render.py` orders `POLICY_FILES` so the scope policy precedes the ClusterRole,
and its comment says why (`render.py:403-408`). But `kubernetes/apply.sh`
applies the whole render with one `kubectl apply -f -` (`apply.sh:626`), and
kubectl does **not** stop at the first refused document: it applies every
other object and reports the failures at the end. If any of the four
ValidatingAdmissionPolicies or their bindings is refused -- a field the server
version rejects, a CEL syntax error, the admissionregistration API unavailable
-- the ClusterRole and its binding are still created, unbounded, and only the
exit status says so. Request-time fail-closed does not cover a policy that was
never created.

Fix, precisely (in `kubernetes/apply.sh`, the `--policies` branch, which this
lane's brief did not name): apply the render in two passes -- every document
except `rbac/provisioner-rbac.yaml` first; then `kubectl get` by name each of
the four `ValidatingAdmissionPolicy` objects and their four bindings, and
`die` unless all eight exist; only then apply `rbac/provisioner-rbac.yaml`. A
test in `tests/unit/worker/test_kubernetes_manifests.py` (or a script test
beside it) that drives `apply.sh --policies --confirm` against a fake kubectl
refusing one policy and asserts the ClusterRole is never applied.

**3.4b Object CONTENT is pinned only for Namespaces, Roles and RoleBindings -- MAJOR.**
The scope policy checks the kind and the **name** of a NetworkPolicy,
ResourceQuota, LimitRange or ServiceAccount, never its spec. A5 could therefore
rewrite `swarm-default-deny` or `swarm-allow-worker-egress` in **every**
personal namespace to allow all egress (the metadata server, the internet,
other namespaces' services), raise a quota or a LimitRange, or annotate a
ServiceAccount. It cannot cross namespaces, grant RBAC, or run a pod, and a
ServiceAccount annotation grants nothing without the GSA's own
`workloadIdentityUser` binding -- so this is a weakening of personal-namespace
isolation for whoever holds the deployer identity, not a path to a
cluster-wide grant.

Fix, precisely: a fifth policy, `swarm-workspace-deployer-networkpolicies`,
matching `networking.k8s.io/v1` `networkpolicies` CREATE/UPDATE for the
deployer, comparing `object.spec` with the render's three specs, as the roles
policy compares rules. The egress policy's DNS address is cluster-specific
(`kubernetes/cluster-network.sh`), so it enters as a placeholder render.py
fills, exactly as the deployer's identities do; the existing parity test in
`tests/unit/worker/test_workspace_provisioner_scope.py` extends to it. The same
shape, with fixed literals, for ResourceQuota and LimitRange; for
ServiceAccounts, refuse any `iam.gke.io/gcp-service-account` annotation other
than the namespace's own `swarm-agent-worker-u-<person>@…`.

**3.4c The residual the RBAC header already states** (cluster-wide `get` by name
on Namespaces, ServiceAccounts, quotas, LimitRanges, NetworkPolicies, Roles and
RoleBindings) is accepted: none holds a secret.

**Verdict, item 3:** no blocker. The policy closes every path to a cluster-wide
grant and to a namespace outside `swarm-tenant-u-*`, and fails closed at request
time. Two majors (3.4a apply-time fail-open, 3.4b unpinned content) and one
minor (3.3 naming) are described above for a Kubernetes lane; none was in this
lane's named files to fix without asking.
