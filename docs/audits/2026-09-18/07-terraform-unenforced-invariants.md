## Findings

I read `CONTRACT.md`, then cross-checked every terraform comment that makes a factual claim about what the application code does against the actual Python source in `apps/`. Four invariants are asserted in terraform comments (and, in three cases, restated in `CONTRACT.md` itself) but are silently unenforced — same failure shape as the `PLATFORM_SERVICE_ACCOUNTS` bug: nothing crashes, nothing alerts, the platform just quietly does less than advertised.

**1. `DISPATCH_TOPIC`/`WAKE_TOPIC` name mismatch — the Pub/Sub fast-wake path has never fired**
`modules/scheduler/main.tf:1-13` and `CONTRACT.md` both describe two independent wake triggers: "Pub/Sub, published by the API the moment work is submitted. Low latency." `terraform/infra/locals.tf:282` implements this by setting `WAKE_TOPIC` in swarm-api's environment. But `apps/swarm-api/swarm_api/settings.py:124` reads `DISPATCH_TOPIC`, and `apps/swarm-api/swarm_api/deps.py:104-105` falls back to a `NullWaker()` whenever that's empty — which it always is, since terraform never sets `DISPATCH_TOPIC`. Every task submission silently skips the publish. **Nobody would notice** because the one-minute Cloud Scheduler safety tick still drains the queue and nothing measures publish-path latency independently of it — the system just runs at "up to 60s slower than designed" forever, which looks like normal tail latency, not a broken feature.

**2. `TENANT_GROUPS`/`ADMIN_GROUPS` never wired — group-based tenant resolution never engages**
`terraform/infra/variables.tf:246-249` and `docs/multi-tenancy.md` describe `swarm_api.auth` as resolving "Cloud Identity group membership to pick the tenant" — the entire elaborate per-group `checkTransitiveMembership` design CONTRACT.md documents. But `apps/swarm-api/swarm_api/settings.py:65-70,121-122` populate `tenant_groups`/`admin_groups` only from `TENANT_GROUPS`/`ADMIN_GROUPS` env vars, which never appear anywhere in `terraform/`. `swarm_common.identity.resolve_tenant()` therefore has no groups to check and every caller falls through to the individual `u-<email>` fallback path. **Nobody would notice** because that fallback path is itself legitimate, working code (it's how the dev tenant `u-bogdan` is meant to resolve) — every request still succeeds and gets *a* tenant, just the wrong one, silently paying from personal quota instead of `eng@saga.xyz`'s shared pool.

**3. `PUSH_SERVICE_ACCOUNT`/`PUSH_AUDIENCE` and `BROKER_AUDIENCE` never set — and the fail-loud guard built to catch exactly this is disarmed**
`modules/scheduler/main.tf:79-81` claims "Pub/Sub presents this OIDC identity, so there is no unauthenticated entry point anywhere," but the app code itself (`apps/scheduler/scheduler/main.py:43-58`, `apps/quota-broker/quota_broker/main.py:149-179`) explains why that's not the whole story: three different service accounts hold `run.invoker` on `swarm-quota-broker`, so Cloud Run's own IAM check can't tell *which* caller called, and without a pinned audience "google-auth SKIPS the `aud` claim entirely." Both apps have a `required`/`hardened` flag meant to crash the process at startup if these vars are missing outside `{dev,test,local}` — but none of `PUSH_SERVICE_ACCOUNT`, `PUSH_AUDIENCE`, `BROKER_AUDIENCE` appear anywhere in `terraform/`, and the only tfvars file that actually deploys to the live shared project (`environments/dev/dev.tfvars`) sets `environment = "dev"`. **Nobody would notice** because the guard was written for a dev/prod split that this repo doesn't have for its one real environment — `saga-agents-staging` is production-shaped but forever classified "dev," so the crash-on-missing-audience protection never triggers there, and the service starts and serves normally with the second auth layer silently inert.

**4. `GKE_CA_CERT_PATH` vs `GKE_CA_CERT_B64` — GKE dispatch (browser/GPU profiles) is permanently unconfigured**
`terraform/infra/locals.tf:288-290` states plainly: "Required for a client running OUTSIDE the cluster. Without both, the GKE backend falls back to `load_incluster_config()`... fails with 'Service host/port is not set'." Terraform sets `GKE_CA_CERT_B64`. But `apps/scheduler/scheduler/dispatch.py:674` reads `GKE_CA_CERT_PATH` — a different name and a different format (file path vs. base64 blob) — so `ca_path` is always empty and the target is never built at all (`apps/scheduler/scheduler/dispatch.py:475`: `DispatchError("GKE dispatch is not configured")`). Notably `apps/reconciler/reconciler/backends.py:497-498` reads the correct `GKE_CA_CERT_B64`, so this is scheduler-only drift. **Nobody would notice** because the scheduler's retry loop treats this as an ordinary transient dispatch failure — the lease goes back to READY and retries every drain, forever, rather than surfacing as a crash — and it only affects the `browser`/GPU/>32GiB profiles CONTRACT.md routes to GKE, so it can sit dormant until the first real browser task is submitted.
