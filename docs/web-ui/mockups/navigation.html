AThe menu: Sky spine

Shown in light on dev, dark on production, as a non-admin, collapsed, and on a phone. Every frame has a fixed theme, so you see both whatever your system theme is. Frames scroll inside their own box on a narrow screen. Tenants, agents and pools are example data.

Variant 2

Sky spine

Owner's pick · 2026-10-01

Idea

An 84px deep-blue spine (#0b3a7a to #06101e, the same in both themes) carries a 44px Hive in its bright gradient, Submit as a sky button, then Overview, Work, Capacity and Admin, with Help, API reads and the avatar at its foot. A 236px panel beside it lists the open section’s pages, with the tenant block, the capacity meter and the user footer. Collapsing hides the panel and keeps the spine; hovering a section shows its pages in a flyout.

Pros

  • The strongest brand moment: the spine is the logo’s gradient, so the product is recognisable from across a room.
  • Collapsed, it still names every section in words, which the 64px rail in Variant 1 cannot.
  • The section-and-page split matches the four-section IA that landed on 2026-09-24 exactly.
  • Help and API reads get words on the spine (#136).

Risks

  • Two columns, 320px in all (84 + 236), is the widest of the three when open. The collapse has to be one click and remembered per person.
  • Two clicks from a page in one section to a page in another, against one in Variant 1. The flyout makes it one hover and one click.
  • On a phone the two columns share a 262px drawer, so panel labels are tighter than on desktop.

CWhat exists, and where every route goes

Today's nav, measured from SECTIONS in App.tsx

Four sections and two utility buttons, over 18 tab routes and three more reached only through links:

  • Overview: one pane, no tab strip.
  • Work: Agents, Workflows, Timeline, Submit a task, Submit a workflow.
  • Capacity: Pools, Runtimes, Profile headroom, Holders, Accounts, Provider quota admin.
  • Admin: Pool limits, Tenants, Platform counts, all admin.
  • Utility: "API reads" and a bare "?" for Help.
  • Not in the nav: the agent inspector (a drawer at #work/task/<id>, with Attempts and Artifacts panes) and the Checkpoint browser inside it.

The router is the hash. SECTION_ALIASES keeps five old section ids alive (agents, pools, activity, history, runtimes), LEGACY maps the old eleven-item nav's hashes, and MOVED_PANES routes panes that changed section.

What the polish issues ask of the chrome

  • #139 phone chrome: the header is about 100px at 390 and the first Agents row starts at y≈402 of 844. Wanted: a compact header, and a sticky strip whose positions never move.
  • #138 page head: one shape everywhere (title, count as a caption, a quiet refresh with its age). The breadcrumb repeats the h1 and its segments are not links.
  • #136: Help needs a word, and Admin rows should stop repeating "admin".
  • #141: wide tables scroll sideways with the name column held below 900px, and records stack. This rail keeps that rule.
  • #117: which screens poll, and how often. Each page head here shows its cadence ("poll 20s").
  • ux-plan §1.4: the old rail was 21 interactive elements on every screen. Variant 1 is 22 when fully expanded and 15 collapsed. It buys one-click reach to every page with those elements.

DDecided

Variant 2, Sky spine

Owner's pick, 2026-10-01, over Flight deck

  • The spine carries the brand (Hive on the logo's own gradient) and the four sections in words, collapsed or open. The panel carries the pages, the tenant, the meter and the user.
  • Collapsing keeps the spine and hides the panel, with a flyout per section, so wide tables (Pools, Tenants, Timeline) can have 84px of chrome instead of 320px.
  • Do not take Variant 3's bell. It implies an alert model this platform does not have.
  • Routing (decided): real History-API paths replace the hash router. On first load, a one-time client redirect maps every old hash (the "Today" and "Also resolves" columns above, including every alias in SECTION_ALIASES, LEGACY and MOVED_PANES) to its new path with history.replaceState, so saved runbook links still land. The server has to serve index.html for every path under the app.
  • Agent inspector (decided): a split view. The list stays on the left and the selected agent fills the right pane, with Details, Attempts, Artifacts and Checkpoints as tabs. The route changes to /agents/live/<id>, so the link is shareable. On a phone it is a full page with a back link. See agents.html.
Alternatives considered: Flight deck and Split chrome
Variant 1

Flight deck

Idea

A full-height labelled rail, 256px, in four groups (Work, Capacity, Admin, Support) under Overview. The top holds who and where: the logo with the environment pill, the tenant switcher, then the Submit button. The bottom holds a one-line capacity meter and the user block. The active row is a sky tint with a left tick, and sub-pages hang from a guide line.

Pros

  • Every page is readable without hovering, and every page has its own row. That answers #136: Help gets a word, not a bare "?".
  • Environment, tenant and Submit sit in the same place on every page, so the operator never has to look for them.
  • The capacity meter puts invariant 1 on screen at all times: 31 of 40 slots leased, and which pool is full.
  • Same bones as AI Studio, so people moving between the two products find things in the same places.

Risks

  • It is tall. With Agents and Pools both open the list needs about 690px, so it scrolls between the tenant block and the meter.
  • It costs 256px of width on wide tables (Pools, Tenants, Timeline). The collapse has to work and has to be remembered per person.
  • The meter can only show one pool. If two different pools bind, it has to pick one, and it will pick the fullest.
Variant 3

Split chrome

Idea

A 54px top bar carries everything that is not a page: the logo and environment, a tenant switcher, a search box ("/"), a bell for capacity alerts, Submit and the avatar. The left rail (224px, on the page background) holds only the menu, so it can stay quiet.

Pros

  • The rail is the narrowest of the three when open, and the top bar costs height rather than width, which suits the wide tables.
  • Search across agents, workflows and pools has a natural home.
  • Alerts get a count and a list behind the bell.

Risks

  • A bell suggests an alert inbox, and this platform has none. The checks are derived on every read and nothing is stored or acknowledged. The design system refused a "Trouble" section for exactly this reason.
  • Two bars of chrome on a phone break the 25% chrome budget in §6.15.
  • Search needs a backend route that does not exist yet (there is no cross-object search in /v1).
