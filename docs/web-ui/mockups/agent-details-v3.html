The agent Details tab, redesigned for the first screen

Measured live on 2026-10-04 at 1440 on a running claude-code agent, the Details pane is 2,770px tall, and almost none of what answers "is this agent all right?" is above the fold. This page redraws the tab in the live console's visual system so that state, elapsed time, what it is doing now, the last log line, memory, CPU and cost all fit in the first 900px. Agents, ids, repos, times and figures are example data; the user is Operator.

2Variant A: a Now card, one stat strip, two columns

Variant A

Answer "is it all right?" in the first screen, and fold the rest

Recommended

The header says the state, the name and how long it has been going, on one line. Under the tabs, a Now card says which phase it is in, the last thing it logged and its latest checkpoint. One stat strip holds the five figures. Then two columns: Progress (phases bar and the last five events) and Resources (thin bars against the limit). Input is folded. When the agent has finished, the Now card becomes the outcome: the PR and files when it succeeded, the failure first when it did not.

Idea

Lead with the state the operator came to check, put the five figures in one strip, and move each detail behind one click, on the card it belongs to.

Pros

  • Everything needed to judge a running agent is above 900px.
  • No new data: every element is a value the tab already reads.
  • One scroll container ends the "blank panel" bug.
  • A not-yet-due value stops shouting in 20px type.

Risks

  • The per-attempt facts (lease, exec, attempt id) leave this tab for the Attempts tab: anyone used to reading them here has to learn one more click.
  • Two columns need about 640px; at the 50% snap on a 1280 screen they stack.
  • The help moves from the page foot into the cards: tests/agentdetail.test.tsx asserts a ? after the state key, and those tests change.

·Loading, empty and error forms of each region

Each region keeps its slot. An unknown figure is a dash with its reason, never 0 (redesign-v2.md, "Honesty rules"). Light, at the detail column's width.

·Variant B: one column with a sticky stat strip

Variant B

The same sections in one column; the strip stays at the top as you scroll

Everything is in the order of variant A, but stacked: Now, Progress, Resources, Input. The stat strip sticks under the tabs, so elapsed, memory, CPU and cost stay in view while you read the events or the prompt. The frame shows the pane scrolled 420px.

Idea

Keep one reading order at every width and pin the five figures, so the strip works like a status bar for the pane.

Pros

  • One layout from 390 to 2560: nothing reflows between snaps.
  • The figures stay visible while you read the prompt or the events.
  • Simpler to build and to test than a two-column grid.

Risks

  • About 300px taller than A: Resources falls below 900px on a running agent, so the first screen misses the bars.
  • A sticky strip plus a sticky header takes about 150px of every scroll position.
  • Wide panes (the 50% snap on a 2560 screen) get long, thin cards with empty right halves.

3Recommendation

Build variant A.

It is the only one of the two that gets every figure, the current phase and the resource bars above 900px on a running agent at 1440. It reads the same data the tab reads today, so it is a layout change, not a backend change. B's sticky strip is a good idea for a narrow pane: A takes it below 640px, where its columns stack anyway.

Small choices made in the frames (each one tenable the other way):

  • The headline is elapsed · attempt n of N in sans next to the title, and the meta line is profile · class · workflow · account. Tenant leaves the header: it is in the panel's tenant tile already. gen and units leave too; they are on the Attempts tab.
  • The full task id is behind a copy id button whose tooltip is the whole id, not printed.
  • The strip's five cells are Elapsed · Attempt · Peak memory · CPU · Cost. Tokens go under Cost as its sub-line, and Checkpoints go to the Now card, because "2 · last 1m ago" is a progress fact, not a total.
  • A live memory figure is the heartbeat's high-water mark so far, labelled "so far · 40s ago", as RunMetrics does today.
  • Carrier gets no chip: no worker reads it yet (CARRIER_NOTE, types.ts:877). It is named in the strategy chip's help.
  • Progress shows the last 5 events, newest first; today's Timeline is oldest first. Newest first is what "what is it doing" needs.
  • Two columns from a 640px pane width; below that they stack and the strip sticks (B's idea).
  • The Output card appears only once result_summary exists or a publish was refused; before that the Now card says "No output yet: written when the attempt ends".

·What the code does not say yet

  • "Cost" while running. cost_usd is written at attempt exit, so a running agent has no cost to show; the frames say "at exit". A live cost would need the worker to write spend on its heartbeat, which it does not.
  • The current phase as a word. phasesFor gives closed and open intervals per attempt; "running now" is read as the open run interval of the latest attempt. No field names the current phase directly.
  • "Last checkpoint 1m ago". attempt.checkpoints is a list of names (string[]); the time comes from the latest checkpoint_completed event on the page, which is capped and oldest first, so on a long run it may be missing. The frame would then say "2 · time not on this page".
  • Two columns' breakpoint. 640px is a choice, not a measurement; the live pane width at each snap was not measured for this page.
  • The 2,770px Today frame is drawn from the description of the 2026-10-04 measurement, not from a screenshot, and its section heights are approximate.
