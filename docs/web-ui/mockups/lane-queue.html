Lanes: the queue, a lane, adding lanes, and the ledger

The owner decided on 2026-10-05 (history V1, epic #640) that the implement → review → fix lane becomes a platform object: it waits for another lane's pull request to merge, holds a file-territory lock, runs the CI-fix loop on its pull request, labels ready when green and reviewed, and closes or comments on its issue. The lane outcome ledger (#639) is designed with it. These are the screens, in two or three variants each, for the owner to pick. The design behind them is docs/lane-queue.md. Nothing here is built, and the section is not in the live console.

All data is example data: the tenant is eng, the user is Operator, the host is swarm.example.com, the repository is example-org/example-api, the group is wave-8, and every number, sha and pull request is invented.

2Queue board

Every lane of a group by state, what each one depends on, and what territory it holds or waits for. The question the board answers first is "what is stuck, and on what".

Variant A

Columns by state, dependencies as chips

Recommended

Idea

A column per state family, in the order a lane moves. A card carries only what explains its column: what it depends on while waiting, the lock it waits for while queued, the round while fixing.

Pros

  • "What is stuck, and on what" is the first thing read: Waiting and Queued are left, each with its reason.
  • Territory and minors sit under the board, where a person decides about them.

Risks

  • Dependencies are chips, not lines; a chain of five reads as five chips. Variant C draws the chain.
  • Six columns need 1,100px; on a phone it becomes a list grouped by state.
Variant B

One table, grouped by state, with a depends-on column

Idea

The Agents table, one row per lane, grouped as Stuck / Moving / Done so the stuck rows lead.

Pros

  • Same table as Agents and Runs; nothing new to learn or build.
  • Sorts and filters; scales past forty lanes.

Risks

  • Seven columns; the reason a lane is stuck is in a cell, not a picture.
  • Territory is a count, so who holds the contested file is one click away.
Variant C

The dependency graph, with locks beside it

Idea

Draw what the laptop kept in memory notes: the chain of merges. Each node is a lane or an external pull request, coloured by state; locks are the list beside it.

Pros

  • A blocked chain is visible as a red root and everything right of it.
  • Shows which lanes merge next.

Risks

  • Lanes without dependencies (most of a wave) are a list beside the graph.
  • A graph needs a layout engine; past twenty nodes it needs panning, which Variant A never does.

3A lane

One lane: where it is in its machine, what it waited for and how long, its pull request and CI, its review, its territory and its issue.

Variant A

A state stepper, then tabs

Recommended

Idea

The lane's machine as a stepper with the time spent in each state, four figures, and tabs for the detail, CI first while it is checking or fixing.

Pros

  • "Where is it and why" in one line; the stepper is also the waiting breakdown.
  • Tabs follow the agent detail page (agent-details-v3, pick A).

Risks

  • The stepper hides PLANNING/PLANNED for brief lanes, so issue and brief lanes draw different steppers.
Variant B

A long page: timeline left, facts right

Idea

Everything on one page, the lane's history as a timeline of its own transitions with the reason each happened.

Pros

  • The timeline says why: which merge released it, which lock it took.
  • No tabs: a screenshot of the page is a full report.

Risks

  • A lane with three fix rounds and two rebase rounds has a long timeline; CI detail is a click further than in A.

4Add lanes

A wave is added at once, because lanes in it depend on each other. Nothing here names a runner profile, image or command: every step is claude-code, chosen by the API (invariant 10).

Variant A

A grid of lanes, one row each

Recommended

Idea

A spreadsheet of lanes under the group's settings. Depends on is a picker of existing lanes, rows above (by key) or an external pull request.

Pros

  • A wave of eight is one screen; dependencies between new lanes are typed once.
  • Cycles and conflicts are shown before submitting, per row.

Risks

  • The brief text needs a row expander; a grid is cramped for multi-paragraph briefs.
Variant B

Paste a lane list, check it, add it

Idea

The format the operator already writes in memory notes, pasted, parsed and checked, so a wave moves off the laptop with no retyping.

Pros

  • Fastest for a person who has the list already.
  • The same text is what the MCP tool and CLI send.

Risks

  • A text format is one more thing to document and keep parsing; a typo is found at Check, not as it is typed.

5Lane ledger

One record per lane (#639): cost summed over every attempt, wall and waiting time, the review, the pull request, CI reds by job, the merge, the issues closed or left. Not the task outcome ledger of Timeline. A null is a dash with its reason, never 0.

Variant A

A table with a totals row

Recommended

Idea

One row per ended lane, every ledger field a column, waiting as a stacked bar, a totals row that says when the cost is a floor.

Pros

  • Every field the owner named is on screen; the CSV is the same table.
  • The stacked bar shows at a glance whether a lane waited on dependencies, territory, capacity, CI or the merge.

Risks

  • Nine columns need 1,200px; on a phone it becomes cards.
Variant B

The group first, then the lanes

Idea

Answer "what did this wave cost and where did its time go" before listing lanes: four figures, two breakdowns, then the rows.

Pros

  • The finding the history analysis needed a day to compute is the first panel.

Risks

  • A single lane's detail is a row away; comparing two lanes needs Variant A's columns.

6Recommendation

Board A, lane detail A, add lanes A, ledger A

  • Board A: the question is "what is stuck, and on what", and columns put Waiting and Queued first with their reason on the card. Board C's graph is worth a toggle later, once waves have long chains.
  • Lane detail A: the stepper is the waiting breakdown, and CI is the first tab when it matters.
  • Add lanes A, with B's paste box as a "Paste a list" button that fills the grid: a wave moves off the laptop without a new text format to learn.
  • Ledger A, with B's four figures above the table.
