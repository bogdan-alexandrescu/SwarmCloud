The diff viewer: five ways to make it easier to reach and to read

The owner asked on 2026-10-08 for a nicer and more easy to use and easy to get to diff viewer that will show the diff per file for any work that has done code edits/commits, as five mock-ups. These are five different approaches, each a complete screen with its entry points, a phone layout, and light and dark themes. The reasoning, costs and lane plan are in docs/design/diff-viewer.md. Nothing here is built.

Fixture data, labelled as such. Every diff on this page comes from real commit dbf6708 on main (2026-10-04, "The agent log is a full-height Logs tab, not a dock over the details", #553): 11 of its 29 files, with that commit's real git show -M --numstat counts and real hunks. That covers an added file, a deleted file and a rename. To keep the page small, a file holds at most 3 hunks and a hunk at most 40 lines; where one was cut, its header says fixture: …. The one binary file is real too (docs/audits/2026-09-23/overflow/05-dock-route-paths-1440.png, 114,775 bytes), but it is not part of dbf6708; it is added so the binary state has a real example. The agent, workflow, run and step names, the step attribution in variant 5 and the review findings in variant 3 are example data. The user is Operator and the host is swarm.example.com.

0Today, measured from the code

The viewer is good at reading one patch: diff/DiffView.tsx has a per-file list with +/− counts and a five-cell bar, unified and split views, collapse with a large-file rule, binary, renamed and mode-change badges, find across the patch, n/p/j/k keys and windowed rows (50,000 lines cost about 300 DOM rows). The trouble is that it is hard to reach, cramped where it opens, and limited to one patch at a time.

Pain points

  • Too narrow for split. Split needs 700px of pane (SPLIT_MIN_WIDTH, DiffView.tsx:137). The inspector is the viewport minus the 320px shell minus the 380px list: 580px at 1280, and about 740px at 1440 before card padding. So split is out of reach at 1280 unless the reader drags the divider or folds the list with [. These figures are computed from styles.css:6203-6215, not measured in a browser.
  • One patch at a time. A workflow or an issue run has one patch per step. Nothing combines them, and nothing says which step changed a given file.
  • Nothing to link to. The URL names the patch but never the file (App.tsx:671-675), and "viewed" is component memory that a remount clears.
  • Counts need the patch read. result_summary.git has per-commit totals (files_changed, insertions, deletions, binary_files) and the patch name. The worker's git log --numstat sees per-file rows and throws them away (agent_worker/gitops.py:1795-1846). So a tab count or file list needs a read of up to 512 KiB first (inspect.py:308).
  • Large patches are paged. Large patches are read in 512 KiB windows, and only files wholly inside a window are drawn (ArtifactViewer.tsx:690-800). The worker discards any patch over 16 MiB (max_patch_bytes, config.py:263) and records patch_omitted.
  • Missing: syntax highlighting (deliberately none: text reaches the DOM as React text nodes only); comments; review findings beside the lines they name (findings are stored as text in verdict_gate, with file and a free-text where at best, verdict.py:202); and a link to the PR from inside the viewer.

1Review page: every file on one full-width page

A GitHub-style review page with a file tree

/changes/task/<id>, /changes/workflow/<id>, /changes/run/<id>

A route of its own, under Work, at full content width (960px at 1280). A file tree on the left with "viewed" ticks; on the right, every file stacked in one scroll with sticky headers. Unified or split, collapse per file and for all files, large files folded. The URL names the file, so a link in chat opens at that file.

Optimises

Reading a large change end to end, the way a reviewer reads a PR. It is the most familiar layout, so it needs no learning.

Costs (data that does not exist yet)

  • A new route and screen.
  • Tree counts before the read need git.files (path, status, +/−, binary, old path) from the worker; today they come from parsing the patch.
  • "Viewed" kept beyond a remount needs storage: localStorage per patch digest, or a per-user API.
  • The PR-body link is a worker change.

Risks

  • It reverses an owner decision. 2026-10-01: "THERE IS NO WHOLE-PATCH READING MODE. A patch is read a file at a time" (DiffView.tsx:15).
  • Windowing has to span files, with sticky headers inside the window: rows.ts has to change.
  • A 16 MiB patch is read in 512 KiB windows, so "every file on one page" is really "every file in this window".

2A Changes tab wherever work happened

Changes, a tab beside Details and Logs

recommended · owner's pick 2026-10-08/agents/<tab>/<id>/changes · /workflows/<id>/changes · /runs/<id>/changes

The shipped viewer, unchanged in what it does, moves from "a button inside a card" to a tab at the full height of the pane, next to the tabs a reader already uses. Opening Changes folds the agent list to its 64px strip (the shipped [), so at 1280 the file gets about 850px and split is available. A summary line leads: totals, the base, the patch, and the PR, linked both ways. The tab count is the file count.

Optimises

Reach: one consistent place, named the same everywhere, one or two clicks from every screen where work happened. It changes the least about reading, because it is the viewer the owner already approved.

Costs (data that does not exist yet)

  • None to ship. The patch artifact and the content route exist.
  • The tab count before a read needs git.files, or the count is a dash until the patch is read. A read on every agent open is up to 512 KiB, so the count comes from the summary or is not shown.
  • A file in the address (?file=) is a DiffView prop (onFileChange, initialFile).

Risks

  • Folding the list on Changes takes the list away from someone comparing agents; it must be remembered, not forced every time.
  • A workflow tab that just lists step patches is a list, not a diff. That is why variant 5 is the workflow content.
  • The credential-refusal rule has to hold in the new tab, which is a second place to keep it (it lives in GitOutcome today).

3Review-first: files by area, the review's findings beside their lines

Read the change against its review

/runs/<id>/review, /agents/<tab>/<review-step>/review

The question a reviewer brings to a diff is "is what the review said true, and was it fixed?" So the page opens on the verdict and its findings, groups files by what kind of change they are, and pins each finding beside the line it names. A finding that names no line is listed and says so; it is never placed on a guessed line. The three findings are example data.

Optimises

Judging a change. It answers "what does the review say, where, and does the diff bear it out?" with no switching between the Decision card and the patch.

Costs (data that does not exist yet)

  • Findings with a place. verdict_gate.findings is stored as text (findings: tuple[str], verdict.py:101). The review's own objects carry file and a free-text where (verdict.py:202) and no line. The worker would have to keep {severity, file, line, side, summary}, plus the patch digest the review read.
  • A finding read against a different patch than the one drawn must say so: a digest check.
  • The fix step's patch, to show "fixed by fix-1" on a finding.

Risks

  • A review's line numbers refer to the patch it read. After a fix round they drift, and a pinned card on the wrong line is worse than none.
  • "Risk" grouping invites a judgement the console cannot measure; it must stay as area and change kind.
  • Pins need a gutter, so split view loses its room.

4A changes drawer over any screen

One Changes chip, a keyboard-driven drawer

no route of its own; ?changes=… on the page it opened over

Wherever there is work (an agent's header, a workflow's head, a run's head) there is one chip: Changes · 12 files +886 −866. It opens an 820px drawer over the page, which stays where it was. The drawer is keyboard-first: n/p file, j/k change, / find, Esc close. It can be pinned open while the page underneath is navigated, and it can switch source between the integrator's patch and any one step's.

A quick look without losing your place: check what a step changed and go back to the graph, the run or the log.

Costs (data that does not exist yet)

  • The chip's counts on every page need git.files, or at least the summary's insertions/deletions plus a file count, which the summary does not carry for uncommitted work.

Risks

  • It overlaps the page, which is exactly what the owner rejected for logs on 2026-10-04 ("does not want the log component overlapping the agent details").
  • Inside the agent split it is an overlay on an overlay.
  • It is a second host for the same viewer, with a second set of Escape and focus rules to keep right.

5The workflow's changes as a files × steps matrix

Every step's patch, stacked by step, with a per-file record of which step changed what

owner's pick 2026-10-08 (with 2)/workflows/<id>/changes · /runs/<id>/changes

A workflow has one patch per step, and the integrator's patch (the PR) is the sum. The matrix puts files down the side and steps across the top, with each cell showing that step's +/− on that file. A step filter narrows rows and columns. Choosing a file shows each step's hunks for it, stacked and tagged by step. A step that changed nothing is a measured zero (hollow ring), and a step whose patch could not be read is hatched; neither is drawn as an empty cell. dbf6708 was one commit: the split across steps is example data.

Optimises

The multi-step case that is this product's own: "which step changed this file, and what did the fix step change after the review?" It is the only variant that answers that.

Costs (data that does not exist yet)

  • Phase 1 needs none: one content read per step that wrote a patch (each step's swarm-work.patch), through the same tenant-scoped, redacting route, in parallel and capped.
  • Cell counts without reading every patch need git.files per step.
  • Line-level attribution needs the integrator to record, per hunk, which input patch it applied (integrated_from). Steps diff against different bases, so their line numbers are not comparable client-side.

Risks

  • N reads for N steps: a 20-step workflow is 20 windows of up to 512 KiB. It needs a cap and "read on demand" for the cells.
  • A carrier: branches step that starts from its parent's branch already holds the parent's work, so the same change can appear twice (dispatch-and-integration.md, "same change twice").
  • Too much on a phone without the card fallback.

7Recommendation

Variant 2 now, variant 5 as its workflow and run page, variant 3's pinned findings once findings carry a line

2 · Changes tab everywhere fixes the problem the owner named, reach, without reopening the 2026-10-01 decision that a patch is read one file at a time. It reuses DiffView whole, needs no new API to ship, and gets room for split by folding the agent list to its strip (the shipped [ behaviour). On a workflow or an issue run the same tab holds variant 5's matrix, because those have one patch per step and a list of patches is not a diff. Variant 3's findings beside the lines follow once the worker keeps a file and line on each finding. Variants 1 and 4 are kept as the record: 1 reverses an owner decision, and 4 duplicates 2 in a second host with its own Escape and focus rules.

Owner decisions, 2026-10-08: variants 2 + 5, then 3; all entry points at once in one lane; syntax highlighting yes (about +6 kB gz, lazy, React text nodes only); phone shows one file at a time with a picker and an All files sheet. Recorded in docs/design/diff-viewer.md §3.
