Config, Secrets, Admin counts and QA environments: proposal E, Guided setup

One of five competing proposals (A to E) for BGD's new Config section, the Secrets scopes, Admin's role-gated pages, Platform counts over time and QA targets with environments. BGD picks one. Every frame below is drawn at desktop width (1440, or this page's width when the window is narrower) and at 390 wide, and the theme control at the top repaints all of them light, dark or as the system says.

What every frame obeys
  • PICKS.md: nothing below 12px, no all-caps, no letter-spacing, a light / dark / system toggle in the panel's user foot, and honesty: an unknown figure is a dash with its reason, never 0.
  • The V2 Sky spine (navigation.html): an 84px spine of sections, a 236px panel of the section's pages, Submit as the sky button, a phone header in the spine colour. The tokens are the console's own (styles.css), light and dark.
  • Example data only. The user is Operator; hosts are swarm.example.com and app.example.com. A stored value is never drawn: it is ••••, and the frames never show one.

Idea

Config is led by what is missing. A setup strip runs across the top of every Config page, GitHub connected → Repositories chosen → Secrets set → People invited, each step measured from a live read, and every page opens with one sentence and one button: its next action. Adding a secret is a four-step wizard (scope → destination → consumer or grant → one-time form). Empty and half-done states are drawn first, because that is where a new workspace spends its first hour. Admin pages borrow the same lead: each opens with what needs an admin now. Platform counts' Over time opens on a sentence, then the chart, then the table.

Pros

  • A new workspace admin never has to know the order: the strip and the lead say it, and a "needed, not set" row names who needs the secret.
  • The wizard asks the questions in the order the design resolves them (scope, then destination, then who reads it), so a GitHub Actions secret cannot be set in the wrong place.
  • Half-done states are explicit: a member is told which step is an admin's, rather than finding a disabled button.
  • One sentence above every chart and table means the answer is readable before the figure.

Risks

  • The strip costs about 56px on every Config page, even when finished. It folds to a one-line "Setup complete" bar, but it is still there.
  • "Secrets set" needs a definition of "needed": this proposal counts a secret that something registered names (an MCP server, a QA target sign-in, the TypeSafe slot) and is not stored. That read does not exist yet.
  • A wizard is slower for an admin who sets ten secrets in a row; the one-time form keeps a "Set another in this place" shortcut to soften it.
  • "People invited" is a softer step than the other three; in a personal workspace it is absent, and the strip has three steps.

S1Navigation: Config in the spine, the panel and the phone menu

Config sits between Capacity and Admin. While setup is unfinished the spine item carries an amber dot and the panel carries the setup meter; each page in the panel shows its own state (done, a count, or what is missing). Settings is reached from the avatar at the spine's foot and now holds only Profile.

S2Config › GitHub access

The page from Work › Access, moved. Not connected is the page's first state, not an error: the lead is the one button that starts setup.

S3Config › Repositories

"Repositories SwarmCloud may reach as you" leads, because it is what the strip's step 2 measures. Add new repository goes to GitHub access › Choose repositories. Below it, repository management: the registered repositories as cards (the picked card layout), with QA targets as the page's second tab.

S4Config › Secrets

The scope picker is Workspace · Yours · Repository. When one name exists in several scopes, yours wins, then the repository's, then the workspace's, and the row shows the override. Each list carries "needed, not set" rows for secrets something registered names, which is what the strip's step 3 counts. Every Set opens a one-time form; no value is ever shown again.

The keys for agents and MCP and GitHub token status are sections of S4a; they are not drawn a second time. On the phone they stack under the list the same way.

S5Config › MCP servers, Config › People and roles, Admin › People and roles

MCP servers and People and roles move from Settings unchanged in body; only the lead and the strip are new. Config's People and roles is this workspace's, for its admins, in a group workspace only. Admin's People and roles is the cross-workspace view.

S6Config › Workspace Settings

Three parts on one page: Settings, Workspace setup (today's Work › Setup, the full checklist behind the strip) and, for an admin, Add a new workspace.

S7Admin › Platform secrets (platform admins only, status only)

Live status from Secret Manager metadata: set or not, enabled versions, age of the newest, and what manages it. There is no Set, no value, no length. A name in the catalogue that does not exist reads "not declared".

S8Admin › Platform counts, with Over time

The count stays a priced button that never refreshes itself. Over time opens on one sentence, then the chart, then the table. Agents are counted by submission day, retries apart; cost is "Estimated cost (list price, not a bill)", an "at least" figure with how many agents reported.

What this proposal decides that the brief left open

  • Settings › API keys moves into Config › Secrets › Keys for agents and MCP (it holds the TypeSafe keys, which secrets-scopes.md lists there); Settings keeps Profile alone, as BGD said. Its two addresses would redirect.
  • "Needed, not set" is a new read: a secret that something registered names and that is not stored. Until it exists, the strip's step 3 would read "—, not measured yet" rather than a count.
  • Who may add a workspace from Workspace Settings is drawn as a platform admin. Whether a workspace admin may also create one is BGD's to say.
