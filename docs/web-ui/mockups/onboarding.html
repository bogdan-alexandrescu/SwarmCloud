Onboarding: connect GitHub as yourself, enable orgs, choose repositories

The owner asked on 2026-10-07 for an onboarding experience, in the console and in the sc plugin, that hand-holds a user through git access, enabling one or more GitHub orgs and choosing the repositories SwarmCloud may read and write, acting as the user. These are the screens, two or three variants each, for the owner to pick. The design behind them is docs/onboarding.md; the token slots and the permission matrix they build on are docs/git-tokens.md. Nothing here is built.

All data is example data: the tenant is eng, the signed-in user is Operator, GitHub account example-user, the console swarm.example.com, the organisations example-org (SAML SSO) and example-lab. No value on this page is a credential, and no frame has a field that takes one.

Setup, Access—this page

1Onboarding entry and checklist

Where a new user meets setup, and how they see what is done and what is next.

Variant A

A checklist card on Overview, until every step is done

Recommended

Idea

A first-run checklist where the user already lands, with the next step's button and the failing step's recovery copy inline.

Pros

  • No new page to find; it disappears by itself when every step is done.
  • The recovery copy is the API's, word for word, so the plugin says the same.

Risks

  • Overview gets taller for a new user.
  • An admin who never works in repositories sees it until they hide it.
Variant B

A Setup page with a vertical stepper

Idea

A dedicated Setup page under Work, with the steps on the left and the current step on the right.

Pros

  • Room for the chooser and the results without a drawer.
  • A deep link per step: the plugin can print it.

Risks

  • One more page in the panel; after setup it duplicates Access.
Variant C

A thin banner on every page, a drawer with the checklist

Idea

Setup follows the user around as a banner until it is done.

Pros

  • Impossible to miss.
  • No new page.

Risks

  • A banner on every page is noise for a user who is waiting on an org owner for a week.
  • The chooser does not fit in a drawer; it opens a page anyway.

2Connect GitHub

The first real step. The token never appears: the page says where it goes.

Variant A

One button, the GitHub App, and where the token goes

Recommended

Idea

Connect is one button; everything the user needs to trust it is on the same page.

Pros

  • Nothing to paste, nothing to rotate.
  • The failure states on return are drawn next to the success.

Risks

  • The PAT fallback is a quiet link; an org that blocks Apps needs it found.
Variant B

Pick how to connect: App, fine-grained token, classic token

Idea

Make the choice visible, because some orgs will force the fallback.

Pros

  • An admin-blocked org has an obvious second path.
  • Honest about what each option costs the user.

Risks

  • Three choices where most users should make none.
Variant C

The hand-off pages: GitHub's consent, then 'return to your terminal'

Idea

Draw the two browser pages the plugin's hand-off lands on.

Pros

  • The plugin and the console share this callback page.
  • Says plainly that the terminal resumes.

Risks

  • GitHub owns the first page; ours can only describe it.

3Org and repository chooser

Owners are installations; repositories are paged from each, searchable, and each chosen Read or Write. A repository not listed can be typed as owner/repo.

Variant A

Owners on the left, one owner's repositories on the right

Recommended

Idea

The org list is the installations; choosing within it is SwarmCloud's own grant.

Pros

  • Org and repository are both visible at once.
  • A repository the user cannot push to says so before Write is chosen.

Risks

  • Two columns are cramped on a narrow screen.
Variant B

One table across every owner, filtered by owner chips

Idea

One list for a user with few repositories.

Pros

  • Fastest for the common case of a dozen repositories.
  • Search crosses owners.

Risks

  • An org with hundreds of repositories drowns the personal account's two.
Variant C

Available on the left, chosen on the right

Idea

Make the allow-list itself the object on screen.

Pros

  • What SwarmCloud may touch is one column, nothing else.
  • Read is the visible default for a repository the user cannot push to.

Risks

  • Two lists to keep in sync for an org with hundreds of repositories.

4Verification results

Clone, Push and Pull request, per granted repository, as ok, missing or unknown, with the recovery copy for anything that failed.

Variant A

A results grid, failures first, with the fix inline

Recommended

Idea

The permission matrix's grammar (ok / missing / unknown) applied to the user's own grants.

Pros

  • Same marks as the Git tokens permission view the console already has.
  • The fix is next to the cell that needs it.

Risks

  • Wide with many repositories; it scrolls.
Variant B

One card per repository, checks running live

Idea

Show the checks as they happen.

Pros

  • Feels alive for the 2-5 seconds verification takes.

Risks

  • Cards hide the cross-repository pattern a grid shows (one org failing every clone).
Variant C

A verdict sentence, then only what needs you

Idea

A sentence first, failures second, details on request.

Pros

  • Shortest path to 'done' for a user with no failures.

Risks

  • The details a support conversation needs are one click further away.

5Access, the steady state

Adding and removing orgs and repositories later, and the tenant's members.

Variant A

Work › Access: connection, owners, grants

Recommended

Idea

Setup's result as a page the user owns.

Pros

  • Add org and Remove are where the owners are.
  • Says plainly what removal does at GitHub and what it cannot.

Risks

  • A third credentials page beside Git tokens and the permission matrix; GT pages stay for tenant tokens.
Variant B

The tenant view: every member's connection, for an admin

Idea

Answer 'who in eng can do what' in one table.

Pros

  • Shows which credential tasks actually used, including the tenant fallback.
  • A failed refresh is visible before tasks pile up.

Risks

  • Admin-only; members see variant A.
Variant C

A tree: owner, then its repositories, toggles inline

Idea

One tree, everything editable in place.

Pros

  • Fewest clicks to change one grant.
  • Pending orgs sit where they will appear.

Risks

  • Verification results get one mark each; the reason needs a hover.

6Recommendation

A everywhere, and B for the admin view of Access

  • Entry A: the checklist where the user lands, gone when ready; its rows are the six step ids the plugin prints.
  • Connect A: one button for the GitHub App, with the fine-grained token fallback a link away (connect B's middle tile, drawn for when an org forces it).
  • Chooser A: owners are installations, repositories are paged and searched per owner, Read or Write per repository, and a typed owner/repo for anything unlisted.
  • Verify A: the ok / missing / unknown grammar the permission matrix already uses.
  • Access A for each user, Access B for an admin: several users per tenant is #780's requirement and only B shows it.
