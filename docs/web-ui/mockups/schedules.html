Schedules: recurring, typed, gated jobs per repository and tenant

The owner asked on 2026-10-08 for a way to "view and fully manage crons" that sweep, plan, execute and merge GitHub issues, run a self-improvement observer, and more, "per repo and fully multi tenant", as a section of the console. These are the screens, two or three variants each, for the owner to pick. The design behind them is docs/schedules.md. Nothing here is built, and the section is not in the live console.

All data is example data. The tenant is eng, the user is Operator, the host is swarm.example.com, and the repositories are example-org/example-api, example-org/example-web and example-org/example-infra. "Today" on the frames is Thursday 2026-10-08. Every dollar figure is an example, not a measurement.

Clickable: on these frames you can open a schedule from list A, pause or resume a row, switch the detail tabs, pick a type template and type a cron expression to see the words and the next five firings (computed in your browser by the same rules the design gives the API, docs/schedules.md §2.3), and approve, reject or expand inbox items.

3Schedules list

One row per schedule, with what the owner listed: type, repository, cron in words, next run, last outcome, spend today, state and waiting approvals. Built-in recurring work that a tenant does not manage here, the index's own cadence, is shown read-only so all recurring work is in one place (docs/schedules.md §8.3). An unknown figure is a dash with its reason; a spend that some attempts did not report is marked partial.

A · Table

list-arecommended

Idea

The table the console already has, with the eight columns the owner named, and the inbox one tab away.

Pros

  • Scans 25 schedules (the per-tenant cap) without scrolling sideways.
  • Sorts by next run, failure or spend.

Risks

  • The repository column is thin for "all registered" scopes; the detail page lists them.

B · Cards grouped by repository

list-b

Idea

Group by repository, the owner's "per repo", with a strip of recent firings per card.

Pros

  • Answers "what runs against this repository" at a glance.

Risks

  • A schedule over several repositories has no single home, so it lands in a catch-all group.
  • Fewer columns per schedule.
  • The firing strip needs a read of the last 14 firings per schedule on every list load.

C · Split: list and detail

list-c

Idea

The Agents pattern (list plus wide detail) for schedules.

Pros

  • Moving between schedules keeps the list in view.

Risks

  • The detail's run history needs width that a split leaves short.
  • Two places to draw one detail.

4Schedule detail

A schedule's run history as a timeline, each run linking to the issue run, workflow or task it made; the budget burn-down for today with its coverage; the gate; settings; and the audit.

A · Tabs

detail-arecommended

Idea

Repository detail's pattern (pick A of repositories.html): a header with four figures, then tabs.

Pros

  • History first.
  • Budget states what it can and cannot stop, in words.
  • Hard stops are listed on the gate, so nobody believes a gate setting turns them off.

Risks

  • The timeline needs every firing's work and their attempts' spans: one read per firing page.

B · One page, timeline first

detail-b

Idea

Everything on one scrolling page, today first.

Pros

  • No clicks for a short schedule.

Risks

  • A sweep's history pushes the gate and audit far down.
  • The page grows with every firing.

5Create and edit

Start from a type template with sane defaults. Then a human-readable cron editor with a preview of the next five firings, the gate within the type's floor, and the budget. Types not yet built are listed greyed with their reason, as the runner catalogue shows unavailable profiles.

A · One page from a template

edit-arecommended

Idea

Most schedules are a type, a repository and a time. Everything else defaults from the type, on one page with the preview beside it.

Pros

  • The whole decision is visible before Create.
  • "Dry run first" is the default start for acting types.

Risks

  • A long form for custom-prompt, whose spec editor needs its own area; it opens the workflow form's editor in a second step.

B · Four-step wizard

edit-b

Idea

One decision per step.

Pros

  • Easy for a first schedule.

Risks

  • Three clicks to change one field on edit.
  • The gate is chosen without seeing the cron, and the review step repeats the form.

C · Drawer over the list

edit-c

Idea

Quick edits without leaving the list.

Pros

  • Fast for a one-field change.

Risks

  • 440px cannot hold the preview and the gate together; creating still needs a page.

6Approvals inbox

One place for every approval: run, plan, merge, proposal and owner holds, across schedules and issue runs. A PLANNED issue run appears here without moving: approving it here is the run's own approve with the digest shown. A waiting item holds no capacity, and it expires (default 72 h).

A · One list, expanding in place

inbox-arecommended on a phone

Idea

A mail-like list; the decision is made in the expanded item.

Pros

  • Works the same on a phone.
  • Approving several is quick.

Risks

  • A plan or diff read in a narrow expansion is cramped on desktop.

B · Split: list and the item

inbox-brecommended on desktop

Idea

The approved thing gets the width: a plan's steps, or a merge's checklist (the merge-step checklist card of agent-detail-2.html).

Pros

  • The checks that make a merge safe are on screen at the moment of approval.

Risks

  • A second layout to build, which the phone does not use.

7Admin › Schedules, all tenants

Admins see every tenant's schedules. They can pause, disable and re-enable them, and pause all of a tenant's. They cannot edit another tenant's schedules or approve its items: those are the tenant's decisions (docs/schedules.md §5.3).

A · One table with a tenant column

admin-arecommended

Idea

The admin's questions cut across tenants: what is R3, what is failing, what costs the most.

Pros

  • Sortable.
  • The tick's own health (lateness, truncation) sits under the table.

Risks

  • Many tenants means a long table; the filters carry it.

B · Grouped by tenant, with rollups

admin-b

Idea

One card per tenant, for the "which tenant is the problem" question.

Pros

  • The tenant-wide pause is one click (typed).

Risks

  • A second click to see any schedule.
  • R3 schedules are hidden inside the cards.

8Recommendation

P3 placement (owner pick 2026-10-08) · List A · Detail A · Edit A · Inbox B on desktop and A on a phone · Admin A

  • P3, the owner's pick: a new spine section, Automate (Overview · Work · Automate · Capacity · Admin) with Schedules and Approvals as its two pages and a badge. P1 (Work › Schedules after Runs) was the recommendation and was not chosen.

  • Admin A sorts across tenants by tier, failure and spend.
