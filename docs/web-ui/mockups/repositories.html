Repositories, and the index every planner reads

The owner asked on 2026-10-04 for a place to register the repositories SwarmCloud works in, an agent that indexes each one on a schedule or when its default branch moves, and that index handed to every planner and step working there, down to "which tests does this diff need". These are the screens, in two or three variants each, for the owner to pick. The design behind them, and why each value is what it is, is docs/repo-index.md. Nothing here is built, and the section is not in the live console.

All data is example data: the tenant is eng, the user is Operator, the host is swarm.example.com, the repositories are example-org/example-api, example-org/example-web and example-org/example-infra.

2Repositories list

One row per registration. Each row answers "is the index good enough to plan from?": freshness against the head polled from the forge, when it was last built, how it is scheduled, and how much of the source the test map covers. An unknown value is a dash with its reason.

Variant A

A dense table, freshness first

Recommended

Idea

The 32px-row table of the picked components, one row per registration, freshness as a state pill in the brand colours, so a stale index reads at a glance.

Pros

  • Every column the brief names is visible without a click.
  • Same table as Agents and Ceilings: nothing new to learn or build.
  • Scales to forty repositories.

Risks

  • Seven columns need about 1,000px; on a phone it becomes a list of rows with freshness and actions only.
  • "Tests mapped %" invites reading it as coverage; its tooltip must say it is index edges, not executed coverage.
Variant B

Cards, one per repository, with the index at a glance

Idea

A card per repository, the way a tenant with a handful of repositories thinks of them, with the test-map bar as the visual anchor.

Pros

  • Reads well with three to nine repositories and on a phone without a second layout.
  • Room for the head sha beside the branch.

Risks

  • Does not scale past a dozen; comparing freshness across cards means scanning a grid.
  • A new card component next to the one canonical set components.html just consolidated.
Variant C

Split view: the list on the left, the selected repository's index on the right

Idea

The Agents pattern (the picked V1 compact list plus wide detail) applied to repositories, so the index is one click from the list.

Pros

  • Same split component, divider snapping and remembered width as Agents.
  • Comparing two repositories' indexes is a click, not a page load.

Risks

  • The list loses columns (schedule, last run) to make room.
  • The detail pane duplicates a cut-down detail page that still has to exist for links.

3Register repository

The credential is never typed here. Registration reads the repository once with the tenant's stored forge token, swarm-tenant-eng-git, to check access and fill the default branch; the form names the secret, and never shows or asks for its value.

Variant A

One page, top to bottom, like the picked task form

Recommended

Idea

One form, stacked, the same shape as the picked Submit forms: the repository first, then what may run in it, then when it is indexed.

Pros

  • The access check runs as soon as the repository is typed, so a bad token is found before anything is queued.
  • Cost of the first index is stated before the click.

Risks

  • A long form for what is usually "this repo, defaults".
  • A typed owner/repo invites typos the access check then reports as 404.
Variant B

A side drawer over the list, defaults folded

Idea

Registering is one field and a button; everything else is a sensible default behind one disclosure, in a drawer that keeps the list visible.

Pros

  • Fastest path for the common case.
  • The new row appears in the list behind the drawer as soon as it is registered.

Risks

  • Defaults hide that indexing spends capacity on a schedule.
  • A drawer is a new pattern; the picked Submit forms are full pages.
Variant C

Pick from what the token can read, then set the schedule

Idea

No typing: list what the tenant's token can already read, so a registration can never name a repository the platform cannot clone.

Pros

  • No 404s from typos.
  • Shows at once which repositories are already registered.

Risks

  • Needs a new forge read (the token's installation repositories), paged, on every open of the form.
  • Lists every repository the token can see to everyone in the tenant, which a fine-grained token's owner may not expect.

4Repository detail

What the index says, how it was built, when it next runs, and who used it. Every figure names the commit it describes.

Variant A

Tabs: Overview, Test map, Hot-spots, Index runs, Settings, Used by

Recommended

Idea

An Overview that answers "can I plan from this?" in the first screen, and one tab per part of the index for depth: the test map is big enough to need its own page.

Pros

  • The staleness banner leads, using the picked page-state tier from states.html.
  • Index runs are drawn with the brand state marks, the same as agents, because they are agents.
  • The tabs map one-to-one to the index's keys.

Risks

  • Six tabs; Used by and Settings could be one.
  • The Test map tab needs a path search to be useful on a large repository.
Variant B

One long page of cards, the test map as a path lookup

Idea

Lead with the question the owner named last, "what tests should run for this change", as a lookup an operator can use before opening a pull request.

Pros

  • The tests:select route gets a screen that shows exactly what agents are told, unmapped paths included.
  • No tabs; territory and commands are visible.

Risks

  • Index runs, hot-spots and Used by fall below the first screen.
  • Typing paths is a developer's task; most operators will use it rarely.
Variant C

Explorer: the module tree, the selected module's facts, and the runs beside it

Idea

Browse the repository the way the index sees it: pick a module, see what it is for, what tests cover it and what changes with it.

Pros

  • Makes the index's quality inspectable module by module, which is how a bad purpose line gets noticed.
  • Impact ("changes most with") is next to coverage.

Risks

  • The most to build: a tree, an inspector and a third column.
  • Schedule and trigger settings are not on the first screen.

5The index inside an issue-run plan and an agent's Details

A plan and an agent both say which index they were given, at which commit, and how far behind its head it was at the time. The chip is the same everywhere: Context used · repo index.

Variant A

A "Context used" chip in the header meta, with a popover

Recommended

Idea

One chip in the meta line the picked Details header already has, beside the other inputs an agent was given, with the facts behind a click.

Pros

  • No new card; fits the v3 header that was just picked.
  • Tests the planner took from the test map are marked where they appear.
  • A stale index shows in the chip itself ("3 behind").

Risks

  • A chip is easy to miss when an operator is asking "why did the plan choose these files?".
  • The popover is the only place the changed-since list is visible.
Variant B

A Context card above the plan

Idea

Make everything the planner read one card the approver sees before the steps: the index, the issue and the open work together.

Pros

  • The approver sees what the plan was based on before approving its digest.
  • Groups the existing open-work snapshot with the new index.

Risks

  • About 120px more before the first step on every run.
  • A second shape for the same facts the agent Details chip shows.
Variant C

Per step: the tests to run for its files, from the index

Idea

Show the index where it changes what happens: each step's selected tests, as the implement step and the merge step will see them.

Pros

  • Draws the "which tests for this change" answer the owner asked for, per step and at merge.
  • Unmapped paths are visible instead of silently missing.

Risks

  • The selection is for planned files; the real diff can differ, so the step's own selection after its diff is the one that counts.
  • Widens every step row by 340px.

6Recommendation

List A, Register A, Detail A, Context A, with Context C's per-step tests folded into the plan step

  • List A is the table the console already has, so it costs least and scales furthest; freshness is the first thing that matters about an index and it leads.
  • Register A states the cost of indexing and checks access before anything is queued. Variant C's picker is attractive but adds a forge read and shows every repository the token can see to the whole tenant.
  • Detail A keeps the staleness banner, the index runs and the schedule in the first screen. Detail B's path lookup becomes its Test map tab.
  • Context A fits the v3 Details header just picked. From Context C, keep the "from the index's test map" marker on a step's tests; the per-step panel can come later.

The owner picks; this is a recommendation. The design choices that do not depend on the pick (registration per tenant, the index under the tenant's prefix, indexing as ordinary capacity-accounted work) are argued in docs/repo-index.md.

8Graph explorer in a repository

Owner decision (b), 2026-10-04: "a way to visualize all of this indexed data and AST and LSP graphs visually in the repository section". Three views in every variant: the module dependency graph (zoom and pan, clustered by package, coloured by hot-spot or by test reach), a symbol call graph centred on one symbol (callers and callees, a depth control, each edge's evidence lsp or ast and its confidence), and the test map (symbol → the tests that reach it). Drawn here as static SVG; the built screen draws the same shapes from GET /v1/repositories/{repo_id}/graph and /symbols, and needs no graph library to read them. Design: repo-index.md §2.5, §3.5.

Variant A

A force-directed canvas with a side inspector

Recommended

Idea

A canvas the operator pans and zooms, clusters drawn as soft rectangles, the inspector beside it answering "what is this module, what does this symbol call, which tests reach it" without leaving the canvas.

Pros

  • The picture people expect from "graph": coupling and hot-spots are visible at once.
  • One canvas for all three views; the chips switch it.
  • The inspector carries the exact numbers the canvas only suggests.

Risks

  • A force layout of 2,000 modules is a hairball: the built screen must start clustered and expand on click.
  • Positions move between index versions unless the layout is seeded by module path.
  • Weakest on a phone; the inspector alone is the mobile view.
Variant B

Hierarchical: a module tree, a dependency structure matrix, and the call graph as an indented tree

Idea

Structure rather than picture: a module tree, a dependency structure matrix that shows layering and cycles exactly, the call graph as an indented tree, and the test map as a symbol × test matrix.

Pros

  • Scales: a matrix of 200 modules is still readable where a node-link drawing is not.
  • Cycles and layering violations are unmistakable.
  • Every cell is a number a test can assert.

Risks

  • Less inviting than a drawing; the matrix needs its one-line legend.
  • The call graph as a tree repeats a symbol reached by two paths.
  • Three panes need the full 1,280px.
Variant C

List-first: symbols in a table, each with an inline mini call graph

Idea

The table the console already has, one row per symbol (or module, or test), with a tiny call graph in each row; the selected row opens a larger inline graph and its test map.

Pros

  • Cheapest to build and to read; search and sort do the navigation.
  • Works on a phone as a list.
  • The exact numbers lead, the drawing supports.

Risks

  • No whole-repository picture: coupling between packages is not visible.
  • A 120px mini-graph is decoration past five edges.
  • The operator cannot pan to a neighbour; they search for it.

9Commit and pull-request impact

Owner decision (c): from a diff to the tests that must run. The chain is the impact query of repo-index.md §4.3a: diff → changed symbols → affected callers (bounded depth) → tests to run, each with the reason it was chosen and the evidence behind it. The same view serves a commit (Repositories › Impact) and a pull request (the run's PR card links here).

Variant A

Four columns: diff → changed symbols → callers → tests to run

Recommended

Idea

Four columns left to right, the chain the query walks, with a count at the top of each and the reason on every test.

Pros

  • The count in each column is the whole story at a glance: 3 files, 4 symbols, 17 callers, 12 of 1,480 tests.
  • Commit and pull request are one screen with a toggle.
  • The cut path is stated, not hidden.

Risks

  • Columns truncate; the operator expands each to see all.
  • Which caller led to which test is in the reason text, not drawn.
Variant B

A tree grouped by changed symbol, with the path to each test

Idea

A tree grouped by changed symbol: under each, its callers and, under each caller, the tests chosen through it with their reasons; four summary figures on top.

Pros

  • The path from a change to a test is drawn, not paraphrased.
  • A test chosen twice is visible as such.
  • Tall rather than wide: works on a narrow screen.

Risks

  • Long for a large change; it needs collapse-all.
  • The summary figures and the tree can disagree in a reader's head when a test is shared; the tree must say "also via".

10The selected-tests gate, one screen per merge policy

How the selection appears where a pull request is judged: the run page's PR card, the swarmcloud/selected-tests check run on GitHub, and the Claude Code side (/sc:swarmcloud in a terminal). Each variant is one policy of repo-index.md §4.4, so picking a screen picks the policy: P1 selected tests are the gate and the full suite is scheduled; P2 selected tests are a fast first gate and the full suite is still required; P3 selected tests gate unless a fallback trigger sends the change to the full suite. The merge step (#295, lane M1a) reads the check like any other required check. Under X2 (the repository's own GitHub Actions) the check shown here is not the dispatched job's own check run, which lands on the default branch commit; it is a check run the workflow's last step posts on the pull request's head sha through the Checks API (checks: write), so it carries GitHub Actions' app_id as the ruleset requires. A commit status could not stand in for it.

Variant A

P1: selected tests are the merge gate; the full suite is scheduled

Idea

Policy P1: the selected tests are the gate. The card says plainly that the full suite is not part of it and when it runs instead.

Pros

  • Fastest merge; CI time scales with the change.
  • The scheduled full run closes the loop with an issue, not silence.

Risks

  • A selection miss lands on main and is found hours later.
  • The ruleset must drop the full-suite checks from required, a change in each repository.
Variant B

P2: selected tests as a fast first gate; the full suite is still required

Idea

Policy P2: the selected tests report first, the full suite is still required. The card shows both, and that merge waits for the second.

Pros

  • Nothing about what green means changes; only red arrives sooner.
  • No ruleset change beyond adding the new check.

Risks

  • Saves no CI time on a green pull request.
  • Two rows that both say "tests" need their labels to stay distinct.
Variant C

P3: selected tests gate, with a full-suite fallback and its reason

Idea

Policy P3: the selected tests gate, except where the graph cannot vouch for the selection; then the same check runs the full suite and names the trigger.

Pros

  • P1's speed for most pull requests, P2's certainty where it matters.
  • Every fallback is explained in the check's summary and in the terminal.

Risks

  • The trigger list must be kept honest, or fallback becomes rare by drift.
  • Operators may be surprised when a one-line fixture change runs everything; the reason line is what answers them.

11Repository Settings: languages, graph, selection policy, and the token that resolves

Additions to the repository's Settings tab (RI0's Detail A keeps its schedule settings). Per language, the grammar and the language server and whether it worked; how deep the graph walks; the selection policy, inherited from the tenant or overridden here; and the git token that resolves for this repository with its capability row (git-tokens.md §3, §5).

Variant A

Cards: languages, graph, selection policy, resolved token

Recommended

Idea

Four cards on the Settings tab: what the indexer could read per language and with what, the graph's depth and cut-off, the selection policy with the ruleset it expects, and the token that resolves here with its capabilities.

Pros

  • Every "why is the graph thin for Go" question is answered by one row.
  • The ruleset mismatch is stated where the policy is chosen.
  • The resolved token is visible exactly where repository access is configured.

Risks

  • Four cards make a long tab; the language card can fold once all are ok.
  • The policy card describes a ruleset it cannot change itself.
Variant B

One form: languages as chips, the token's capability row as a one-row matrix

Idea

One form, the brief's four additions as rows, the token's capabilities as a one-row matrix under it.

Pros

  • Compact; matches the picked task form.
  • The capability row reads exactly as a row of the permission matrix (section 13).

Risks

  • Language detail is squeezed into chips; the failure reason is a tooltip.
  • No room for the ruleset-mismatch warning beside the policy.

12Git tokens

Owner request (d), 2026-10-04: different git tokens per repository and per user or tenant, and what each can do. The list by scope — tenant default, repository, user — with the account each acts as, its forge, expiry, when it was last verified and the repositories it covers; and registering or rotating one. A token's value is never displayed: at most its last 4 characters, recorded once. Design: git-tokens.md. Whether the console may accept a value at all is the owner's decision (§4.2): variant A draws the paste box, variant B the command-line path that keeps today's rule to the letter.

Variant A

A table grouped by scope, with a register drawer that takes the value once

Recommended

Idea

The Agents-style table, grouped by scope, with the register drawer open: the paste box masks the value, says it goes to the server once, and keeps only the last 4.

Pros

  • Every column the owner named on one screen.
  • Expiry in the brand warning and failure colours.
  • Rotate and Verify now on every row.

Risks

  • The paste box is a new path for a forge token; the owner decides it (git-tokens.md §4.2).
  • A tenant with many users makes the User group long; it needs filtering.
Variant B

Cards by scope, and registration handed to the command line

Idea

Cards per token, filterable by scope, and registration as a three-step handoff to the command line, so the value never crosses the console or swarm-api.

Pros

  • Keeps the owner rule of 2026-09-25 exactly: stored only with create-secrets.sh --stdin.
  • No new path for a secret to leak through.
  • Cards read well on a phone.

Risks

  • Registration needs a terminal and gcloud access; a user without them asks an admin.
  • Cards scale worse than a table past a dozen tokens.

13Permission matrix: what each token can do in each repository

Computed server-side from the forge — the repository's permissions, an App token's granted permissions, a classic PAT's X-OAuth-Scopes, the expiry header — and served as ok, missing or unknown with a reason, never as the token (git-tokens.md §5). Hover any cell for its reason; an unknown is grey, not green.

Variant A

A matrix grid: tokens × repositories, one cell per capability

Recommended

Idea

Every token × repository × capability in one grid, grouped by repository, the resolving token marked.

Pros

  • The whole tenant's access in one screen; a missing cell is impossible to miss.
  • Each cell's reason is a hover away.
  • The same row appears on a repository's Settings (section 11).

Risks

  • Eleven columns need the full width; on a phone it becomes perms-b's cards.
  • Rows for tokens that never resolve add noise; a "resolving only" filter is needed.
Variant B

Per-repository cards: which token each action would use, and what it lacks

Idea

One card per repository, one line per action SwarmCloud takes there, naming the token that would be used for it under the tenant's resolution order and what it lacks.

Pros

  • Answers the operator's real question: "what will happen in this repository".
  • Shows the resolution order at work, including a user token falling through to the tenant default.

Risks

  • The tenant-wide picture is spread across cards.
  • Toggling R1/R2 here previews an order; it must not look like it sets it.
Variant C

A checker: "can SwarmCloud do X in repo Y?"

Idea

A question box: pick an action, a repository and (optionally) a user, get yes / no / not known, the token that would be used, why, and what would fix it.

Pros

  • The question an operator actually asks, answered in one sentence.
  • Includes the fix, which neither grid nor cards say.
  • Smallest to build: one route, POST /v1/git-tokens:check.

Risks

  • No overview; it only answers what is asked.
  • Easy to read a "not known" as a yes; it must stay grey and say why.

14Recommendation, second pass

Graph A, Impact A, Settings A, Git tokens A or B by the owner's paste-box decision, Permissions A; the gate policy is the owner's alone

  • Graph A is the picture the owner asked for, with Graph B's dependency matrix as a second tab once repositories pass a few hundred modules, and Graph C's symbol table as its search.
  • Impact A: the four counts are the answer; Impact B's tree is what "Show path" should open.
  • Gate A, B or C is not recommended. They are policies P1, P2 and P3 (repo-index.md §4.4), and choosing what "green" means is the owner's decision.
  • Settings A puts the ruleset mismatch beside the policy, which Settings B has no room for.
  • Git tokens A if the owner allows a token value through the console (git-tokens.md §4.2); B if not. Nothing else on either page depends on that.
  • Permissions A as the page, with C's checker as its search box and B's card as the mobile layout.

The owner picks; this is a recommendation.
