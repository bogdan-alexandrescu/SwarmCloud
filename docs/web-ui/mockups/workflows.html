AThe workflow list, full width

Owner's pick, 2026-10-01: V2, a list page and a page per workflow. This is the list at /workflows, with 30 workflows in mixed states. Names, owners and costs are example data.

Idea

One row per workflow across the full width: rollup state mark, name, stage shape, a steps-done bar with n/m, the runner mix, cost, owner and age. Failed and dead-lettered rows carry a second line naming the failing step and its reason. Segments filter by Running, Finished, Failed and All with counts; search, owner and profile filters sit beside them, and all of it is in the URL so a link reproduces the view.

Pros

  • Answers "what is running, what finished, what broke" without opening anything.
  • The failing step and reason are in the row, so triage starts from the list.
  • Filters in the URL survive the round trip to a workflow and back.

Risks

  • Thirty rows with a second line on failures is long; Finished could collapse to one line per row.
  • The runner mix needs the step list for every workflow on the page, which is the same read today's board already makes.

CThe recent-workflows switcher in the panel Owner's pick · 2026-10-01

Decided: yes. Under Workflows in the Sky spine panel, the five workflows you opened most recently, each with its state mark, then "All workflows →", so moving between workflows does not need the list. It appears in every V2 frame above, on the list and on one workflow, light and dark.

Idea

Five recent workflows under the Workflows item, plus "All workflows →". It is the list's first rows for you, not a second list to maintain.

Pros

  • Switching between two or three workflows during an incident is one click.
  • No new read: it comes from the list read and the browser's own history.

Risks

  • With the panel open, the graph and the step card no longer fit side by side and stack instead.
  • Remembered per browser for now, so it does not follow you to another device until the per-person API store lands.

DStep tints

Steps use the same state vocabulary as everything else: a pale tint of the state's hue across the card, a 4px edge in that hue, and the state's own mark. Teal-green for the four states that hold capacity, violet for parked, red for failed and dead-lettered, grey for succeeded, queued, ready and cancelled. The same tints apply to graph nodes, minimap nodes, table rows and timeline spans.

EWhat exists today

Workflows today, from Workflows.tsx, WorkflowViews.tsx, dag.ts

  • One read pair: GET /v1/workflows?limit=100 and GET /v1/tasks?limit=200, joined by task id. Attempts per step are read for at most 12 tasks. The screen does not poll; it re-reads only after a step is stopped.
  • A board with Rows / Graph / Timeline / Table. A row shows the state, id, progress, shape (1 → 5 → 1), runner mix, spend, age and a "cancel requested" flag, and expands in place.
  • The rollup state is derived: UNKNOWN if a step was not read (never stored), RUNNING if any step holds capacity, then the worst terminal state, then READY > PARKED > QUEUED. When the step-read budget runs out, rows read "state unread".
  • The graph lays steps out in stages, collapses wide stages into a band, has Auto / Figures / Details / Names zoom and a minimap. A node shows its name, state, wait or run time, runner, and at Figures tier ran, cost, tokens and checkpoints; it has its own Stop.
  • Edges are order, staged (a file passed from a parent) or declared.
  • There is no "cancel workflow" control, although POST /v1/workflows/{id}/cancel exists. Only a step can be stopped.

What #405 asked (owner, 2026-09-30), and what superseded it

  • #405 tinted steps light green (succeeded), light blue (live), cream (waiting), light red (failed) and grey (cancelled). Superseded on 2026-10-01: steps use the brand state colours instead (section B). Unknown stays dashed amber.
  • A light tint across the whole card plus a stronger left edge in the same hue, at AA contrast.
  • On graph nodes, minimap nodes, table rows and timeline spans. In dark mode, low-opacity deep tints rather than washed-out pastels.
  • Kept from #405: one token set, --state-*-bg / --state-*-edge, and a test that every state maps to exactly one token. No PR has implemented it yet; the hex values here are mine.
  • From docs/workflows.md: under fail_workflow a failed step cancels every step that has not started, and running steps finish. Under continue, only its dependents are cancelled.

FDecided, and what is still open
