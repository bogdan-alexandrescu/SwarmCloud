Submitting from a GitHub issue, and switching tenant

Two features decided after the batch-2 mock-ups. Part 1 (#454): a GitHub issue as the input on Submit, with plan approval and auto-merge chosen at submission, auto-merge off by default. Part 2 (#447): the tenant switcher, shown only to people in more than one tenant group. Both are built on the approved Submit and Navigation mock-ups. Every task, workflow, issue, repository, tenant and person drawn here is example data.

1Submit from a GitHub issue (#454)

The owner’s decisions, from the issue body and its 2026-10-01 comment: a submission names owner/repo#N or its URL; the issue is read with the tenant’s own swarm-tenant-<tenant>-git credential, never a caller’s token; a planner reads it and every open issue and PR and decides one agent or a workflow; plan approval (required by default) and auto-merge (off by default) are both chosen at submission and nowhere else; the CI fix-round cap defaults to 3, choosable 1–5; the same works from the console, sc run --issue and /sc run --issue.

Idea

From a GitHub issue becomes the third card on /submit and gets its own one-page form at /submit/issue: name the issue, see what was read, pick a runner, then decide what it may do on its own. The submission lands on a run page that links the issue, the plan comment, the status comment, the workflow or task, and the PR.

Pros

  • Typos, closed issues, PR numbers and missing access are caught before anything is created.
  • Leaves the task and workflow forms as approved; the planner, not the person, decides task or workflow (#454).
  • Both submission-time choices sit together, with the default spelled out.

Risks

  • The pre-submit read needs something that can read swarm-tenant-<t>-git before any worker runs; on main only the worker does (open question 1).
  • The planner reads the issue again later, so an edit between preview and plan is possible; the plan shows what it read.
Variant 1B

An issue as a source inside the existing task and workflow forms

Idea

No new choice. The task form’s step 2 (and each workflow step’s prompt) gets a switch between a written prompt and an issue reference, and plan approval and auto-merge join step 3.

Pros

  • No new page; one fewer card on /submit.
  • A workflow author can feed one step from an issue.

Risks

  • The person picks task or workflow before the planner has read anything, which contradicts #454: the planner decides one agent or a workflow.
  • Two approved forms grow two more controls each.
Variant 1C

Send the reference; the planner reads the issue

Idea

The same third choice and form as 1A, without the pre-submit read. What the issue says first appears on the PLANNED run page, under Read from the issue.

Pros

  • swarm-api never reads a tenant’s git secret, which keeps today’s boundary: only the worker does.
  • Less to build: no read route, no preview states.

Risks

  • A typo, a closed issue or a PR number costs a planner run and is found after submission.
  • The brief’s “shown before submit” becomes “shown before approval”; with plan approval set to Auto, nobody sees it before work starts.

Recommendation: 1A

It is the only variant that shows the issue before anything is created and leaves the shape (task or workflow) to the planner, as #454 decided. Its one real cost is the pre-submit read; if the owner keeps swarm-api away from tenant git secrets, 1C is the same screens with the preview moved to the run page.

Small choices made in the frames

  • Auto-merge is drawn visible and disabled with “not available until #295” today, exactly as #454 orders; after #295 it is an off-by-default switch.
  • The fix-round cap is shown in the form (default 3, 1–5), because the owner’s comment lets the submitter choose it.
  • The button says Plan this issue, not Submit, since what happens first is planning.
  • A closed issue warns and needs an explicit Plan it anyway; a PR number is refused and pointed at the task form.
  • 404 is worded as “not found or not visible”, because GitHub uses 404 for private repositories it will not show.
  • The run page lives at /runs/<id> under Work, with a new Runs entry; the id prefix run_ is invented.
  • The run page names a missing workflow or PR as “none yet” instead of hiding the row; cost per run is a dash, as it is not served.
  • Shortcut I for From an issue, beside T and W.

2The tenant switcher (#447)

Decided on 2026-10-01: the panel’s tenant block becomes a switcher, shown only to people in more than one tenant group; everyone else keeps the static label with copy-id. The API lists your tenants with GET /v1/tenants/mine, the console sends the choice on every call (for example X-Swarm-Tenant), and the API honours it only for a verified membership, refusing with 403 otherwise. With no header, today’s first-match rule applies unchanged.

Idea

The tenant block that already sits under the wordmark (.sk-tenant) becomes a button for members of several groups: name, “tenant · 1 of 3”, a swap mark, and a list on click. The collapsed spine shows a tenant tile under the logo; the phone header shows a chip that opens a bottom sheet.

Pros

  • The owner’s 2026-10-01 pick in the Navigation mock-up; nothing else in the shell moves.
  • Scope sits above every page and every count it changes.
  • Single-group people see exactly what they see today.

Risks

  • The collapsed tile adds 52px to the spine; on a short window the lower spine items scroll sooner.
  • A switch with work in flight on screen (a draft, an open agent) needs the two handled cases above, or it will mislead.
Variant 2B

The switcher lives in the panel’s user footer

Idea

Tenant joins the person in the footer, as an account menu: “operator · eng” with the swap mark. The top of the panel goes back to pages only.

Pros

  • A familiar account-menu pattern; who and as-whom in one place.
  • Frees about 50px at the top of the panel.

Risks

  • Scope moves to the bottom, under the meter, far from the figures it changes; easy to miss which tenant you are in.
  • Reverses the 2026-10-01 placement and collides with the theme toggle’s footer.
Variant 2C

A tenant chip in the page head, top right of the work area

Idea

Scope as a chip in the page head (App.tsx’s head, §B3), on every page, in the same place whether the panel is open, collapsed or a phone drawer.

Pros

  • Always visible, including with the panel collapsed, without changing the spine.
  • Reads as “this page, as this tenant”.

Risks

  • The head already carries the breadcrumb and page actions; a chip on every page competes with them.
  • Single-group people would need a static chip too, or the head changes shape by person.

Recommendation: 2A

It is the placement the owner picked on 2026-10-01 and the only one that keeps scope above the figures it changes without adding chrome to every page. Collapsed, the spine tile keeps it visible; on a phone, the header chip does.

Small choices made in the frames

  • The list shows display name, tenant id and the group email, so two tenants with similar names cannot be confused.
  • Switching keeps the section and page, reloads every read, dims the old rows until the new answer arrives, and shows a dash, never the old figure, in the meter.
  • An open object from the old tenant closes with a message rather than being re-fetched as the new one.
  • An unsent form is kept and re-labelled with the new tenant; the submit button names it.
  • A toast confirms the switch with a one-click way back.
  • Admin stays with the person, not the tenant (is_admin is computed from admin groups, auth.py), so switching does not change the admin badge.
  • No per-tenant colour: the initial tile is enough, and colour stays reserved for state.
  • The collapsed tile uses 12px text under the initial, per the type rule.
