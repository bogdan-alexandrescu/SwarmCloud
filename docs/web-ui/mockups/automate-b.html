Automate: proposal B, One inbox, decision first

One of four competing proposals (A to D) for BGD's redesign of Automate. BGD picks frames across the four. Every frame below has the same id in every proposal (A1 to A7). The theme control at the top repaints the page and every frame light, dark or as the system says, and so does the toggle in each frame's panel foot.

Idea

Automate opens on Waiting on you. That is one list of everything that needs a person: approvals to decide, schedules their spend tripwire paused, and schedules that are failing. It is ordered by urgency: anything expiring within a day, then anything that has stopped work, then the rest by time to expiry. The schedules follow underneath. Every waiting row opens a decision page laid out in one order: first the question in one sentence, then the evidence in numbered cards, then Approve / Deny with a reason in a bar pinned to the bottom of the screen. You cannot reach the buttons without the evidence above them.

How it differs from the console today

  • Today Schedules opens on a table, and the waiting items sit on another tab (Approvals) or in Overview's card. Here the Schedules page leads with them, and the list also holds schedule trouble, which today only the State column shows.
  • Today an approval opens in a split pane: a list on the left, facts and buttons on the right. Here it is a full page with an address of its own (/automate/approvals/apr_…), and the buttons are pinned under the evidence.
  • A schedule page is cards (Config E) instead of five tabs. History, spend, cadence and gates show together; Audit and Settings fold into the cards.

Risks

  • The inbox shows waiting approvals on Schedules as well as on Approvals. That is the same data twice. It is kept because each page serves a different need: the inbox is the to-do list, Approvals is the record.
  • The urgency order is a rule this proposal invents. A tripwire pause can outrank a merge that expires in two days. BGD may want approvals always first.
  • A merge's check counts are not served today (see the new fields at the end).
Tabs: SD1 stands
  • Automate keeps its two pages, Schedules and Approvals (SD1, docs/schedules.md §6.1). Proposal B does not merge them. It changes what Schedules opens on: the inbox, and then the schedules.
  • Approvals stays a page of its own because it is the record: decided, denied, expired and superseded items, filtered by kind. That list grows without end and would push the schedules off the landing. The inbox shows only what is waiting.
  • State words are lower-case words: waiting, approved, denied (the API's rejected), expired, superseded, active, paused, paused by its tripwire, failing, never fired. Nothing below 12px, no all-caps, and an unknown figure is a dash with its reason.
  • Example data is read as of 2026-10-26 09:12Z. A5's approval and its schedule are the real records named in #2417. The other rows are examples.

Fields

·New fields this proposal needs

Every other figure on this page is served today by apps/swarm-api (routes/schedules.py, routes/approvals.py) or derived from served fields, as each caption says.

1 · merge.checks on a merge approval: {passed, failed, pending} at the head

What: the pull request's check counts at merge.green_sha, read when the approval is read. Why: A5 card 1 draws "10 passed · 0 failed · 0 pending". Today the detail serves green_sha, requirements_met and requirements_unmet[], which say "green" but not how many checks it took. If it is not added, card 1 keeps the checklist and draws the count as a dash with "not served".

2 · work[].pull_request on a firing's issue-run work item

What: the PR number an issue run opened, and its state (open, merged or closed), copied onto the firing's work item. Why: A2's history draws each firing's PR. Today the PR lives only on the issue run, so 50 firings would need 50 extra reads.

3 · superseded_by and head_sha_now on a superseded approval

What: the id of the request that replaced it, and the head it was replaced for. Why: A5e links to the newer request and names the new head. Today a superseded item says only "a newer request replaced it" (Approvals.tsx).

4 · reason_files on a hold: which matched file each reason came from

What: {workflows: [".github/workflows/unit-weights-refresh.yml"], shared: ["scripts/lib/common.sh"]}. Why: A5 card 2 would pair each reason with its file. This page does not pair them: hold.reasons[] and hold.matched[] are drawn as two lists, as served. The field is optional, and the card says so.

Not new: what the inbox and the schedule page compose

The inbox needs no new route. It is GET /v1/approvals (pending items, with expires_at) together with GET /v1/schedules (state: auto_paused with pause.code for the tripwire, and consecutive_failures with policy.max_consecutive_failures for failing), sorted in the browser by the urgency rule. A2's next firings are POST /v1/schedules:preview with the schedule's cron and timezone. The time-left bar is computed from requested_at and expires_at. One contract-adjacent note: policy.max_consecutive_failures is read by the tick but cannot be set through the API body. A2 draws it as "2 of 3" and A3 does not offer it.
