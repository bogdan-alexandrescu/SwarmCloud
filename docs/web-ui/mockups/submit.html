DWhat exists today

Submit a task today, from Submit.tsx and Dispatch.tsx

  • A tab inside Work. Reads /v1/capacity; sends POST /v1/tasks.
  • 1 "Choose a runner": radio rows with class, units, backend and the provider key needed; a disabled profile stays listed with its reason; nothing is preselected.
  • 2 "Say what it should do": key/kind/value rows, offer buttons per profile (prompt, command, paths, timeout_seconds…), and "a setting of your own". #119: the offers do not read as "add" controls; consider one "Add setting ▾" menu.
  • 3 "Choose what happens to the result": Collect (default) or A PR per step; integrate is hidden for a task, with a link to workflows; a repository url when a PR is chosen.
  • A side panel says "Ready to send" or "Not ready to send". Success says "Created at READY" and "That is not a running agent — it costs nothing until admission takes it."

Submit a workflow today, from SubmitWorkflow.tsx

  • Reads /v1/capacity and /v1/stats (for the step limit); sends POST /v1/workflows.
  • 1 "Lay out the plan": stages headed "first" and "then"; each step has a name, a runner, settings and "waits for everything in the stage above", with optional staged files from a parent.
  • 2 "Choose what happens to the work": all three strategies. No JSON editor, no on_step_failure, no priority.
  • #118: step 1 preselects the first profile (browser), so a pristine form can be sent; the stage connector is a stray 2×14px tick; "add a step here" wraps and leaves an empty cell.

EDecided

Owner's picks, 2026-10-01: the chooser page, the one-page task form, the stacked workflow form

  • The spine's Submit button opens /submit; N from anywhere opens it too, then T or W picks. The forms are /submit/task and /submit/workflow.
  • Recent submissions on /submit show an empty state until the API keeps a per-person list of submissions.
  • No runner is preselected in either form; a pristine form cannot be sent (#118).
  • Settings use one "+ Add setting ▾" menu with a note per key, on tasks and on every workflow step (#119).
  • After submitting, the success panel links to the new task in /agents/waiting/<id> or the workflow at /workflows/<id>.
  • The workflow form gains both on_step_failure and priority (owner, 2026-10-01). Step 2 adds "If a step fails": Fail the workflow (fail_workflow, the API default: steps not started are cancelled, running steps finish) or Continue (continue: only the failed step's dependents are cancelled). And "Priority": a whole number from −100 to 100, default 0, applied to every step. Both show in the summary.
Alternatives considered: a menu from the spine button, a four-step wizard, stages as columns
Variant 1

A menu from the spine button

Recommended

Idea

A small menu anchored to the spine's Submit button: Submit a task, Submit a workflow, and the last two things you submitted to start from.

Pros

  • One click from any page, no page load before choosing.
  • Keyboard: N, then T or W.

Risks

  • Recent submissions need a per-person list the API does not keep yet; until then the menu has two items.
Variant 2

A four-step wizard

Idea

Runner, settings, result and review as four screens.

Pros

  • One decision per screen; good on a phone.

Risks

  • Hides the runner's capacity while writing the prompt.
  • Slower for people who submit many tasks.
Variant 2

Stages as columns, left to right

Idea

Each stage is a column, flowing left to right.

Pros

  • Many stages fit side by side on a wide screen.

Risks

  • Does not match the top-to-bottom graph in Workflows.
  • Unusable on a phone without turning it back into rows.
