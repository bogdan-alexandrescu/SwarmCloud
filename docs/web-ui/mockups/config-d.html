Proposal D: every Config and Admin page is a list with an inspector beside it

BGD asked on 2026-10-23 for four or five complete, competing designs of every new and changed page before anything is built. This is proposal D, the Split-pane inspector. Every Config and Admin page is a master list on the left and an inspector on the right, the shape the console's Agent inspector already has (agents.html V1, picked 2026-10-01). Actions sit in the inspector, the list is keyboard driven, and on a phone the inspector is a pushed page. The frames are drawn 1440 wide on a desktop and 390 on a phone. A desktop frame is scaled down to fit a narrower window, and below about 900px it scrolls sideways instead. They follow the page's theme toggle, at the top here or in any frame's panel foot, so each one is drawn once and read in light and dark. The user is "Operator", the hosts are swarm.example.com and app.example.com, and every name and figure is example data.

DIdea, pros and risks

Idea

One page shape for all of Config and Admin: a master list, 380 to 640px wide and filterable, and an inspector holding everything about the selected row, every action included. The list is the page's index and the inspector is the page's work. Secrets is one list of every secret the person can see, across scopes, with the columns scope, destination, consumers and last set. The scope picker (Workspace · Yours · Repository) and the destination switch (Agents | GitHub Actions) are filters on that list. The inspector holds the grants, or the GitHub destination and its branch rule, and the one-time form opens inline in it. The keyboard works the same everywhere: / filter, ↑↓ move, Enter open, Esc close, plus one letter per inspector action. On a phone the list is the page and the inspector is pushed over it with a back link.

Pros

  • One shape to learn. GitHub access, Repositories, Secrets, MCP servers, People, Workspace Settings and all seven Admin pages read alike, and the console already has this shape in the Agent inspector.
  • It is dense. A workspace with 60 secrets fits on one screen with no paging, and the shadowing rule (person, then repository, then workspace) shows as adjacent rows plus one line in the inspector.
  • The address carries the selection (/config/secrets?scope=repository&repo=…&dest=actions&sel=…), so a selected row can be shared as a link, as /agents/live/<id> can.
  • The one-time form never leaves its context. The grants and the name stay in view while the value is typed, and closing the form puts you back on the same row.
  • Admin's workspace-admin view is the same list, filtered. Nothing is redrawn for that role.

Risks

  • It needs a wide screen to pay off. From 1100 to 1280px the inspector is narrow, and the GitHub Actions environment card and the QA run group's two columns get tight there. Below 900px the inspector becomes the pushed page.
  • Some pages want the whole width: Platform counts' chart and the QA run group's columns. Here the master list folds to a 300px index, and that costs space.
  • A filterable list of every scope invites "show me everything", and a workspace with many repositories gets long. The page opens on the workspace and Yours scopes, with repositories collapsed to one group each.
  • Actions are one click further away than on a card-per-item page: select, then act. The letter shortcuts give that click back to keyboard users only.
  • Selecting a row must not fire a read the person did not ask for. GitHub Actions secrets are read live from GitHub (secrets-scopes §3.3), so the inspector reads them only on Enter or a click, never on arrow keys.

S2Config › GitHub access

The master list is the connection plus every GitHub owner the person can reach: their account, the orgs where the App is installed, orgs waiting on an install request, and orgs without the App. The inspector holds the owner's installation and its actions. "Choose repositories" is the same split one level down: the owner list narrows to an index, and the inspector becomes onboarding.html's chooser A.

S3Config › Repositories

The list has two views on one switch. "Registered in eng" is the workspace's registry. "Reachable as you" is today's "Repositories SwarmCloud may reach as you", from Work › Access. Add new repository sits at the top of the list and opens Config › GitHub access › Choose repositories, because a repository is chosen there and nowhere else. The inspector keeps repositories.html's picked detail tabs, A. Its Secrets tab is a summary that opens Config › Secrets filtered to the repository, so the secrets are drawn in one place only.

S4Config › Secrets

One list of every secret the person may see, filtered by scope (Workspace · Yours · Repository), by kind (For agents, Keys for agents and MCP, Browser sessions, GitHub tokens) and, for a repository, by destination (Agents | GitHub Actions). No value, length or characters of a value are ever drawn: a set secret shows "set" with who set it and when. When one name exists in several scopes, the rows sit together and the inspector names the winner: the person's, then the repository's, then the workspace's. Every Set opens a one-time form in the inspector.

S5MCP servers, People and roles in Config, and Admin › People and roles

The bodies are today's (McpServers.tsx, WorkspacePeople.tsx, People.tsx), redrawn in the list-and-inspector shape. Config › People and roles is this workspace only. It is drawn for a group workspace's admins and is absent in a personal workspace. Admin › People and roles is the cross-workspace view. A platform admin sees every person and every workspace, and a workspace admin sees the same list filtered to the workspaces they admin.

S6Config › Workspace Settings, with Workspace setup and Add a new workspace

The list has three groups: the workspace's settings (today's Settings › Workspace), Workspace setup (today's Work › Setup checklist, one row per step), and, for a platform admin only, Add a new workspace (BGD, 2026-10-23 23:57Z). A workspace admin sees their own workspaces' settings with no such row, and a member requests a workspace at Workspace setup › Request your workspace. The inspector shows one setting, one step with its fix, or the new-workspace form.

What this proposal asks of the build, and what it leaves alone

  • No store, route or contract changes for the layout. Every list row is a row the routes already serve or that secrets-scopes §6.2 adds (GET /v1/secrets/overview), and every inspector action is one of the routes named there.
  • The master-list component (filter, keyboard, selection in the address, pushed page under 900px) is built once and used by every Config and Admin page. That shared component is this proposal's main build cost.
  • A row that cannot be managed (can_manage: false) still opens its inspector, read-only, with one line saying who can change it. The API is the gate. The console only describes the rule.
