## F01 · merge step FAILED `inputs_unavailable` · 2026-10-25T18:45:33Z

### What happened

Agent `task_23b8c1ad8b73491db5f8`, workflow `wf_ec5e702e9b804c648e79`, a single
`merge` step submitted by bogdan@saga.xyz. It was submitted `READY` at
18:45:07, leased and dispatched to GKE at 18:45:08, and running at 18:45:31.
Two seconds later it failed:

```
upstream task task_f6f7a52554b7417baa86 is not one this task declares as upstream, so the state routes refuse to read it
```

It had one attempt, exit code 1, and empty stderr. Its served
`result_summary.merge` is `{"pull_request_task": "task_f6f7a52554b7417baa86",
"refusal": {"code": "upstream_unreadable", ...}}`. The agent it was refused is
`SUCCEEDED`. It is step `fix` of workflow `wf_65d0c7a575884c5f8551`, the
integrator that skipped its agent on a MERGE verdict and pushed `d52620f1` to
**PR 2368** ("Closes #2365"). That PR was still open and unmerged at about
01:00Z.

### Root cause

**A product defect: a missed reader at isolation cutover b1.**

The worker side. `apps/agent-worker/agent_worker/merge.py`, `run_merge`
(1362-1372). The merge's first read is the agent that opened the pull request:

```python
opener = ctx.fetch_upstream(target.pull_request)
...
except InputUnavailable as exc:
    summary["refusal"] = {"code": "upstream_unreadable", "message": str(exc)}
    return _outcome(TaskState.FAILED, EndCause.INPUTS_UNAVAILABLE, summary, str(exc))
```

On a tenant whose state goes through swarm-api, `fetch_upstream` calls
`inputs._route_upstream` (`apps/agent-worker/agent_worker/inputs.py`
476-491). That function turns a `StateRefused` with code
`upstream_not_declared` into the message above.

The refusal. `apps/swarm-api/swarm_api/attemptstate.py`,
`AttemptState.upstream` (1657-1677):

```python
declared = {d for d in task.get("depends_on") or [] if isinstance(d, str)}
declared |= {k for k in _mapping(metadata.get("input_from")) ...}
declared |= {k for k in _mapping(_mapping(metadata.get("dispatch")).get("input_parents")) ...}
if upstream_task_id not in declared and not self._derived_upstream(attempt, task, upstream_task_id):
    raise refused
```

`_derived_upstream` (1679-1704) adds four more reads: the index base, a
`builds_on` ancestor, the gate review and a workflow ancestor. The last three
admit only agents **of this agent's own workflow**.

Why the target is in none of them. The single-step workflow is a
**merge-only continuation**: `issueci.merge_workflow`
(`apps/swarm-api/swarm_api/issueci.py` 1411-1431) submits `"strategy":
"direct-pr", "continues_task": pushed_by` with one `merge` step. For that
shape `validation.merge_sources` returns `MergeSources(continued_task,
continued=True)` (validation.py 2891-2892). `MergeSources.depends_on()` then
returns `[]` (2834-2837):

```python
def depends_on(self) -> list[str]:
    if self.continued or self.named:
        return []
```

`service._step_dispatch` signs the target as
`dispatch.merge_target.pull_request`, a key that `AttemptState.upstream`
never reads. So the id the worker must read is signed, tenant-checked at
submission (`continuation.resolve_continuation`,
`issueci.merge_target_unbound`), and refused anyway.

Why only now. `terraform/environments/dev/dev.tfvars:732` has
`state_via_api_tenants = ["u-bogdan", "eng"]` (cutover b1, prepared
2026-10-23). On direct Firestore the same read succeeds. The cutover runbook
already names this class: `docs/runbooks/isolation-cutover.md` says a 403
`upstream_not_declared` is "either a missed reader (file it) or a probe for
another agent". This is a missed reader.

### Blast radius

Every merge-only continuation on a state-routes tenant (`eng`, `u-bogdan`)
fails at its first read, every time: issue-run auto-merge cannot merge on
`eng` today. In this window that is F01 and F02. The same gate also refuses
the merge step's later reads of its own document and its rounds' agents (#2373,
PR 2375). Those reads sit in bare `except` blocks in `merge.py` (`_own_doc`,
`_recorded_fix_heads`), so they degrade silently instead of failing.

### Covered already?

**Partly, and only by accident.**

- #2373 is a merge step refusing its own fix round's head as `head_moved`. It
  does not name merge-only continuations or `inputs_unavailable`.
- PR 2375 (open and unmerged at 00:56Z, head `3ad6451b`) finds the same
  `upstream_not_declared` root for the merge step's own and its rounds'
  reads. It changes only `merge.py`, so that `head_moved` names the records it
  could not read. The real fix sits in the PR body as an **unapplied** patch:
  a fifth derived read, `_is_merge_fix_record`, in `attemptstate.py`. It asks
  BGD to choose between that patch and rolling `eng` back off cutover b1.
- Traced by hand, that patch would admit F01's target: the target continues
  nothing, so it is the root the patch serves. But none of its five route
  tests uses the continuation shape (`depends_on=[]`, a
  `merge_target.pull_request_workflow` of another workflow), so nothing holds
  it there.

### The fix

This is a change to the tenant-isolation read gate, so it is **BGD's
decision** and needs the review CLAUDE.md requires for tenant isolation. It
is the same decision PR 2375 already asks, and should be answered once.

- **Recommended.** In `AttemptState.upstream`, add the signed
  `metadata.dispatch.merge_target.pull_request` (a string) to `declared`, and
  apply PR 2375's `_is_merge_fix_record` for the later reads. The existing
  `doc.get("tenant_id") != attempt.tenant_id` check still refuses another
  tenant's agent. The worker still verifies the opener's signed spec against
  `merge_target.pull_request_workflow` (`merge._verify_opener`).
- Red first, in `tests/unit/control_plane/test_attemptstate.py`, with its
  `opened`, `seed_task` and `_refused` helpers:
  - `test_upstream_serves_a_merge_only_continuations_target`: a merge agent
    with `depends_on=[]` and `dispatch.merge_target = {"pull_request":
    "task_round", "pull_request_workflow": "wf_earlier"}`, and `task_round`
    seeded for tenant `eng` in `wf_earlier`. It expects 200 and is a 403 at
    `f8fa083`.
  - Two controls that must stay refused: the same target seeded for another
    tenant, and an `eng` agent the merge target does not name.

### Severity and confidence

**S3.** Issue-run auto-merge is blocked on `eng`, but a person can still merge
the PR or label it `ready`. It is not S0: the gate fails closed, which is the
isolation guarantee working.

**Confidence: high.** The path is deterministic, and the served refusal code,

What would raise it: a list of `eng` merge agents since 2026-10-23, to show

### Root cause

**A by-design refusal, working exactly as written. The design is wider than
its reason.**

- The refusal: `merge.py`, `run_merge` (1385-1391), `if verdict.verdict !=

  re-review's verdict: `REREVIEW_ROUNDS = 1`, validation.py 834, and
  validation.py 828-834 says a second NOT_YET stops the workflow at its merge
  "with the pull request open for a person".
- Why the review said NOT_YET: the rendered-review gate (owner decision
  #2184), `apps/agent-worker/agent_worker/verdict.py`:

  ```python
  UI_PATH_PREFIXES = ("apps/swarm-ui/", "docs/web-ui/")          # 643
  def is_ui_path(path: str) -> bool:                              # 689
      return isinstance(path, str) and path.lstrip("/").startswith(UI_PATH_PREFIXES)
  ```

  This is a bare prefix test with no exemption for `__tests__/` or
  `*.test.tsx`. #2337 limits it to the lane's own files
  (`ui_paths_in_own_files`, read from `result_summary.git.own_files`), and
  that part worked: it ignored PR 2349's real UI files that GitHub's diff of
  PR 2374 also lists. The only own file it counted is a vitest file.
- Why the lane touched that file: its own pre-publish vitest failed after
  22:00Z on cause E (F10, F11), and the implementer pinned `Date` in the test.

  could fix.

Is the design still right? Its reason is "reading markup is not seeing a
page". A vitest file changes no rendered page, and both reviewers and the
fixer said so independently. The rule is right for components, stylesheets
and `index.html`, and too wide for test files.

### Covered already?

touches only a UI test fails the same way. No answer was readable at 01:00Z.

### The fix

The fix is **BGD's decision** (product behaviour, owner decision #2184).

- **Recommended: B, plus a waiver (A) for PR 2374.**
  - **A. Waive once.** Merge PR 2374 by hand, or re-run its review on
    `claude-code-browser`.
  - **B. Test files are not UI.** `is_ui_path` returns False for a path under
    `apps/swarm-ui/` in a `__tests__/` directory or ending in
    `.test.ts(x)` / `.spec.ts(x)`. `docs/workflows.md` §"A UI lane's MERGE
    counts only from a rendered review" records why.
    - Red first, in `tests/unit/worker/test_review_rendered_gate.py`:

    - Controls that must stay gated: `apps/swarm-ui/src/App.tsx`, a `.css`

- **C (its own issue).** Stop spending rounds on a profile-only finding:

### Severity and confidence

## F04 · implement step FAILED `outputs_missing` (`published_nothing`) · 2026-10-26T00:35:51Z

### What happened

Agent `task_551c841e19f04a90aae5`, workflow `wf_ae6ed35d1f344542b956`, one
`implement` step on `claude-code`. It is lane **REPOS-FOLLOWUPS-MERGE**:
"merge origin/main into PR 2319's branch, no rebase, no force-push".

- The attempt started at 23:35:01 on a clone pinned detached at `b81501c`,
  PR 2319's head. Its `clone_timed` event says `"pinned": true`, and the
  agent's first `git status` read `HEAD detached at b81501c`.
- The agent's stdout log shows what it did:
  1. `git checkout -B swarm/task_2a486dc14a7a4a718afc`, a local branch named
     exactly as PR 2319's branch.
  2. `git merge origin/main`, three conflicts resolved to main's side, merge
     commit `821a6f36c`. Its tree equals `origin/main`.
- At 23:54:48 its pre-publish vitest failed on cause E (F10/F11). The fix turn
  committed `d88907b2e`, loosening the two accounts tests' regexes.
- The second pre-publish round ran at 00:35:42 and everything passed, over
  `changed_files: 259`. That is main's own progress since the PR's base, not a
  wrong base.
- A final checkpoint at 00:35:44, then at 00:35:51, exit code 0:

  ```
  published_nothing: HEAD moved off this task's branch (to swarm/task_2a486dc14a7a4a718afc); nothing of this task's was published
  ```

### Root cause

**A product defect: two answers to "which branch does this step publish?"**

- The guard. `apps/agent-worker/agent_worker/lifecycle.py`,
  `Worker._head_moved` and `Worker._fetched_line` (6058-6077). Ending on
  another branch counts as a move when that branch is a fetched line. The one
  exemption is the step's own branch:

  ```python
  own = self._publish_branch_name()
  if own and end == f"refs/heads/{own}":
      return False
  ...
  return read_origin_ref_as_data(repo, end) is not None
  ```

- `Worker._publish_branch_name` (6113-6123) returns the amender's author
  branch, otherwise `continuation_mod.publish_branch(...)`, which here is
  `swarm/task_551c…`. **It has no `publish_to_pr` case.**
- `Worker._publish_git` (13176-13197), the real push, has one (#2183):

  ```python
  onto_pr = (self._publish_to_pr() if not pr_role and self._opens_pull_request() else None)
  if onto_pr is not None:
      branch = onto_pr.branch(cfg.git_branch_prefix)
  ```

So the worker would have pushed to `swarm/task_2a486…`, while its guard called
that same branch "a line the agent fetched" and refused. `_fetched_line`'s own
docstring says the step's own branch is never a fetched line because "its
commits are this task's own, which the descent check … still bounds". It just
asks the wrong function which branch that is. `_adopt_tool_pushed_tip` reads
`_publish_branch_name` too and has the same blind spot.

The agent did nothing wrong. `git checkout -B <the PR's branch>` is the natural
way to "update PR 2319's branch". Had it committed on the detached HEAD, the
work would have published. The prompt's only publish text
(`runners/cliagent.py`, `PUBLISH_PARAGRAPH`) says "the worker publishes your
committed branch", which arguably invites the checkout.

**One inference.** That the step carried `publish_to_pr: {number: 2319, …}` is
inferred from the root step with no `repository_ref` whose clone was pinned
detached at the PR's head. Only the `publish_to_pr` clone path produces that
(`lifecycle.py` 5571-5614). The signed dispatch block was not readable. The
task document's `metadata.dispatch` would settle it.

### Blast radius

Any `publish_to_pr` step whose agent checks out the PR's branch by name.
`publish_to_pr` is new (#2183, 2026-10-24). In the 50 newest `FAILED` agents
(back to 2026-10-25T04:18Z, read at about 00:58Z), only this one fails with
"HEAD moved off". The cost was 61 minutes of runner time, about 40 of them
checking main's changes, and an account lease. PR 2319 was not updated.
Nothing was published and no patch was written.

### Covered already?

**No.** PR 2378 covers only the incidental vitest failure. #2373/PR 2375, #2366
and PR 2374 are other guards.

### The fix

No owner decision is needed; this is a correctness fix inside the worker.

- **Change.** In `lifecycle.py`, one helper decides the push branch, used by
  both `_publish_git` and `_publish_branch_name`: the amender's author branch;
  else `onto_pr.branch(prefix)` when `not pr_role and
  self._opens_pull_request() and self._publish_to_pr()`; else
  `continuation_mod.publish_branch(...)`. The descent check still bounds the
  work: HEAD must descend from the PR head it started on, and
  `_check_pull_before_push` re-reads the PR before pushing.
- **Red first,** in `tests/unit/worker/test_publish_to_pr.py`: a `DIRECT`
  lane whose agent runs `git checkout -B <PR branch>` and commits. Assert
  `published` is True, `branch` is the PR branch, and there is no
  `head_moved`. At `f8fa083` it ends `head_moved == <PR branch>`.
- **Controls** that keep #2094 standing: the same lane checking out another
  fetched branch, and a lane without `publish_to_pr` checking out a fetched
  branch, both still `head_moved`.

### Severity and confidence

**S3.** A re-run that stays detached, or a laptop merge, works around it.
Confidence is **high** on the mechanism and **high-medium** that the step was
`publish_to_pr` (see the inference above).

### Root cause

**A by-design refusal. The guard is right, and its ending is wrong.**

- The refusal. `merge.py`, `_merge_with_token` (1716-1724): `accepted = …
  _accept(merger, head=head, pinned=pinned, fix_heads=fix_heads, …)`, and `if
  head is None or accepted is None: return run.refuse("head_moved", …)`.
- What it accepts. `_accept` (2176-2193) takes:
  - an exact match on the pinned head, this step's CI-fix and conflict
    rounds, the CI fixer's records, or swarm-api's recorded fix heads;
  - or any of those under base merges walked by `_updates_onto`, where every
    commit must satisfy `commit.by_github` (693-695): `self.verified and
    committer_email == "noreply@github.com"`.

  So a clean merge of main made on a laptop is refused, while
  `auto-merge.yml`'s `is_pure_base_merge` accepts the same commit from any
  committer by checking its parents and tree.
- The wake. `apps/swarm-api/swarm_api/mergewake.py` `_read` returns

## F18 · application (push) on `main` @ 3ebaa4a · 2026-10-25T15:26:50Z

### What happened

Run 40206969879, `unit tests (3/9)`, on a GitHub-hosted ubuntu-24.04 runner:

```
FAILED tests/unit/worker/test_live_browser_relaunch.py::test_a_real_process_that_dies_on_a_signal_gives_its_signal_and_its_last_stderr_lines
  AssertionError: assert -9 == -<Signals.SIGSEGV: 11>
```

### Root cause

**A test defect, dependent on load. The mechanism is inferred, and one read
confirms it.**

- The test: a real child writes 30 stderr lines, then runs
  `os.kill(os.getpid(), signal.SIGSEGV)`. It is awaited through
  `gate_main.Browser(proc, Pipe()).exited(10)` under `asyncio.wait_for(main(),
  20)`.
- The code under test: `apps/agent-worker/agent_worker/livegate/__main__.py`.
  - `Browser.exited`:

    ```python
    try:
        await asyncio.wait_for(self.proc.wait(), timeout)      # 10 s here
    except asyncio.TimeoutError:
        await _stop_process(self.proc)
    ```

  - `_stop_process(proc, timeout=5.0)` sends `terminate()`, waits 5 s, then
    sends `kill()`.
- So -9 is only possible if the child had not exited within 10 s **and**
  ignored SIGTERM for 5 more. The total, 16 s, is under the outer 20 s, which
  is why the test failed on its assertion rather than on a timeout.
- A process that ignores SIGTERM but dies to SIGKILL right after a SIGSEGV is
  the signature of a **core dump in progress**. While a dump runs, the kernel
  drops every signal but SIGKILL, and a SIGKILL during the dump makes the exit
  status SIGKILL. On a loaded `pytest -n auto` runner with a piped
  `core_pattern` helper, the dump can stall.
- The file's usual time is 2.1 s (`unit_test_durations.json`), so a failing
  run of 16 s or more would stand out.

**What would settle it:**

- This run's JUnit time for the test, in artifact `unit-durations-3`
  (12604111308). At 15 s or more, the timeout-and-kill path is confirmed; near
  0, an outside SIGKILL (OOM) is the cause instead.
- `cat /proc/sys/kernel/core_pattern` on a hosted runner.

### Blast radius

It made main's `python-unit` red, which skipped `build images` and caused F17.
In this window it failed only once.

**Production side note (inferred, S4):** the real gate waits `EXIT_WAIT_SECONDS
= 5.0`, so a Chromium SIGSEGV on a node with a slow core helper would be
recorded as `signal_SIGKILL`, the wrong cause.

### Covered already?

**No.** The test is unchanged at `f8fa083` and is not in `tests/flaky.txt`.

### The fix

- **Change.** The child makes itself non-dumpable before signalling:
  `prctl(PR_SET_DUMPABLE, 0)` through `ctypes`. The kernel then writes no core
  and the exit is -11 at once. (`RLIMIT_CORE=0` does not stop a piped helper.)
  Also assert that the elapsed time stays well under 10 s, so a slow exit fails
  loudly instead of passing as -9.
- **Red first.** A real red run cannot be forced, because it depends on load.
  The honest red is a deterministic fake-process test: `wait()` blocks past
  the timeout and `terminate()` is ignored, so `exited` returns `-SIGKILL`.
  That pins the path F18 took. Then the real-process test changes as above.

### Severity and confidence

**S3.** Confidence is **high** that the -9 came through `exited(10)` → the 5 s
SIGTERM grace → `kill()`, and **medium** that a core dump is why SIGTERM was
ignored, pending the JUnit time.
