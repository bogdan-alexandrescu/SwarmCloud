# `tests/browser` — the headed-browser UX/UI suite

```bash
make ui-test                          # everything, headed
scripts/ui-test.sh --headless         # same, no window (CI, or over ssh)
scripts/ui-test.sh --only pools-pools # one view, for a tight loop
scripts/ui-test.sh --update-baseline  # record today's findings as the baseline
```

Report: `build/ui-test/report.txt`. Machine-readable: `build/ui-test/findings.json`.
Every request the page made: `build/ui-test/requests.json`. Screenshots per view
per viewport: `build/ui-test/screenshots/`.

| exit | meaning |
|---|---|
| 0 | no findings |
| 1 | findings, every one of them already in `baseline.json` |
| 2 | **at least one NEW finding** — something got worse |
| 3 | the harness could not run (no browser, no bundle, no node). Never a pass. |

Two failing codes rather than one, deliberately. This UI has real defects today —
`docs/web-ui/evidence/` records sixteen clipped and sixteen ellipsised elements on
*every* view — so a suite that returned the same `1` forever could never tell
anyone that something had got worse. `baseline.json` is not approval; it is the
line between "still broken" and "newly broken", and deleting an entry is how a fix
gets locked in.

---

## Why this exists, and why it does not live in `make test`

Over three days this platform produced a run of defects that every existing test
missed, and they all had one shape: **both ends built, the seam between them never
executed.** A runner that never put `SWARM_ARTIFACTS_DIR` in the child
environment. A decoder that dropped five spend fields while a passing test
asserted they were `None`. A handler reading `app.state.token_endpoint` that
nothing ever set, with a suite that assigned it in its own fixture.

A UI suite that mocks `fetch` reproduces that blind spot exactly. So this one does
not mock anything the product owns:

* it serves the **production bundle** (`npm run build`), not the dev server, so
  `import.meta.env.DEV` is false and the fixture path in `api.ts` is dead code —
  the app really issues `/v1` requests;
* those requests cross a **real socket** to a real HTTP server on the same origin,
  which is the topology the load balancer will present (static at `/`, swarm-api
  at `/v1`);
* the response bodies are generated by `fixtures.py`, which **calls**
  `swarm_api.codec`, `swarm_api.headroom` and two of the route handlers rather
  than restating what they return;
* `fetch.ts` therefore does its real work: classifying real statuses, real
  content-types and real socket failures.

`make test` must stay offline, credential-free and seconds long — it is the gate
CLAUDE.md names before anyone may say a change is done, and it has to be cheap
enough that nobody is tempted to skip it. This suite needs node, a built bundle
and a headed Chromium and takes minutes. Folding it in would make the cheap gate
expensive, and the first time Chromium was missing somebody would add a skip
guard — which is how `tests/integration` rotted for 95 commits. Hence a separate
target, and this paragraph.

## Why it is not "the deployed UI"

There is no deployed UI. `docs/web-ui/01-reachability.md` is explicit: no load
balancer was ever built, so no browser can reach swarm-api, and nothing serves the
bundle. `apps/swarm-ui/README.md` says the same in its last line. The most
faithful available target is the production bundle on the production topology,
which is what this drives. When a load balancer exists, the one thing that has to
change is the origin.

## What it asserts

### 1. Layout integrity — per view, per viewport
`1600x1000, 1440x900, 1280x800, 1024x768`. Four kinds, each a different failure:

* `doc-hscroll` — the page scrolls sideways.
* `overflow-right` — an element starts on screen and ends past the right edge,
  with no scrollable ancestor. Nothing reaches the rest of it.
* `clipped-x` — content wider than its box with `overflow-x: hidden`. This is the
  sixteen-per-view finding in `docs/web-ui/evidence/`: API paths squeezed from
  ~300px into 158px.
* `text-truncated` — `text-overflow: ellipsis` with content that overflows. A
  deliberate choice that still loses information; a route or an id truncated in
  the middle cannot be copied, read out or searched for.

### 2. Identifier fidelity
No `task_`/`wf_`/`att_`/`lease_` id may be rendered through a `text-transform`
that changes it. The check computes what the transform does to the id and
compares — `text-transform: lowercase` over an already-lowercase id is not a
defect, and flagging it would be noise the first reader learns to skip.
`QuotaDetail.tsx` already documents the reasoning; this makes it enforceable.

### 3. Nav / heading agreement
The `h1` must equal the active nav label or the selected tab label. It does not
today: nav **Pools** shows h1 **Capacity**, nav **History** shows h1 **Activity**.

### 4. The honesty rules — asserted in the browser, against a failing control plane
The most valuable part, and the reason the control plane is a server rather than a
route intercept: the check that matters most is a **content-type check on a 200**,
and proving it needs a real header on a real response.

| scenario | what the screen owes the reader |
|---|---|
| `capacity-down` (500) | no bare number anywhere the failed read fed; the failure named *as a failure to read*; the data-source strip showing which route died |
| `unreachable` (socket destroyed) | no metric tile showing a figure; `unreachable` copy, which is distinct from every 4xx because it is never the caller's fault |
| `session-expired` (200 + `text/html`) | the sign-in redirect must not parse as an empty, healthy platform. This is `status.sh` reproduced in a browser |
| `leases-down` (one of seven reads 503s) | the header says *how many* reads failed; the screen names the check that could not run; the strip shows the route |
| `spend-partial` (one attempts read 503s) | no total presented as complete when one of its inputs is missing |
| `healthy`, two tasks | an **unmeasured** attempt renders an em dash and a **measured zero** renders `0`. A mock run that really cost nothing and a run whose result could not be parsed must not be the same pixel |

### 5. Keyboard and focus
Every visible interactive control reachable by `Tab`; a visible focus ring on each
(outline *or* box-shadow — the check is "is there a visible change", not "did you
use the property I expected"); the drawer trapping focus while open and restoring
it on close.

### 6. Contrast, and greyscale
WCAG AA over the **composited** background — the first opaque ancestor background,
composited downwards, read off `<html>` when there is none. Assuming white would
report every colour in this product's dark theme as a failure.

Greyscale is a separate check and a sharper one: for each pair of state tones on
screen, if they are near-identical in luminance **and** carry the same non-colour
mark, they are reported. Hue alone is not the failure — hue alone *without a
second signal* is, and a hollow dot or a distinct glyph is a second signal. These
states are the difference between running and dead.

### 7. The API seam, at runtime
Every path the browser actually requested is matched against the `@router`
declarations read out of `apps/swarm-api/swarm_api/routes/`.
`test_runtimes_screen.py` already does the static half by scanning `api.ts` for
path literals; this is the dynamic half, and it sees paths that are assembled at
runtime from a variable, an encoded id or a `URLSearchParams` — which a literal
scan cannot. `service_accounts` versus `service-accounts` is exactly this class.

A path the control plane has no fixture for is reported too. It is a hole in this
suite rather than a product defect, but a screen quietly fed a 404 is a screen
whose audit means nothing, so it is named rather than swallowed.

## Operating notes for the browser driver

These cost several hours on 2026-09-21 and are enforced in `browse.mjs` rather
than left in a runbook:

* **`BROWSE_HEADED=1` goes in the environment, never as `--headed`.** The flag is
  folded into a config hash; once set, every later call that does not repeat it
  reads as a different configuration and restarts the daemon, taking the pinned
  tab with it mid-run.
* **Never delete `~/.gstack/browse.json`.** `buildRestartEnv` reads `mode: headed`
  out of it to survive an autostart. Without it a run falls back to `launched`
  mode — `chromium.launch()` plus `newContext()`, with no cookie jar — and
  nothing says so. The report prints the mode it actually got for this reason.
* **`js` runs against the ACTIVE tab, and the active tab drifts.** Every script
  this suite evaluates carries an origin guard and refuses to act when
  `location.origin` is not the target. During the manual session a relative fetch
  on the wrong tab posted to `accounts.google.com`.
* **`js` is stored and read back** through a window property rather than trusted
  to return a value directly.
* **The command's exit status is advisory; the page's own URL is the truth.** A
  daemon still settling aborts the incoming navigation and then completes it, and
  the first command after Chromium launches can outlast the client's health-check
  window — "Headed server running (PID n) but not responding" was printed for a
  navigation that had already succeeded. Believing the status navigated five more
  times to the page it was already on.
* **Only one process may talk to the daemon.** Every `browse` invocation that
  cannot reach one starts one, so a status check in the shell and the runner's
  first call a second later are two processes racing to spawn the same server.
  That is what "Another instance is starting the server, waiting… Timed out" is,
  and it leaves a half-started daemon that answers nothing for the rest of the
  run. `scripts/ui-test.sh` therefore never calls `browse`; the runner does all
  of it.
* `about:blank` cannot be used as a nudge — `about:` is a blocked scheme in this
  driver ("Only http:, https:, and file: URLs are permitted").

## Proving a check can fail

A test that cannot fail is not a test, so every check here was put in front of a
deliberate regression and had to catch it. The loop is:

```bash
# 1. break something
printf '\n.ctl-nav-sections { min-width: 2400px; }\n' >> apps/swarm-ui/src/styles.css
# 2. run only what covers it (rebuilds the bundle first)
scripts/ui-test.sh --only overview-now --sections matrix
# 3. the report must show it as NEW, and the exit code must be 2
# 4. put it back
git checkout -- apps/swarm-ui/src/styles.css
```

`--only` and `--sections` exist for this loop and for working on one category.
Both mark the run partial and neither can ever print PASS — a shortcut that can
go green is a button somebody presses instead of running the suite.

What that loop caught, in the checks themselves:

* **Two audits were silently truncated** by a backtick inside a comment inside
  their template literal. The literal closed early, the rest became module-scope
  JavaScript, and the error said `ReferenceError: metric is not defined` —
  nothing about backticks, nothing about which audit. Every audit source is now
  compiled at import, so a truncated one fails immediately with its own name.

* **The greyscale check was wrong twice, and only running it said so.** First it
  read `getComputedStyle(el).color` on the element carrying the tone class — but
  a rule like `.ctl-metric.is-good .ctl-metric-value` colours a *child*, so every
  tone read as the inherited body colour and it reported 36 collisions that did
  not exist. Reading the first tinted descendant instead was no better: that is
  the *label*, the same grey on every tile. It now subtracts the colours common
  to all tones and compares only what each tone contributes, and it compares the
  *widest* gap rather than the narrowest — taking the narrowest meant one shared
  grey was enough to declare a collision.

  With that fixed it reports one thing, and the thing is real: in the light
  theme `--ok` (#1a7f37) and `--bad` (#cf222e) sit at **1.05:1** in luminance.
  Green and red, identical in greyscale, on tiles that carry no glyph and no
  other mark. That is the classic red/green failure, and it was invisible to
  every other check in this repository.

* **Disabled controls were being reported for contrast.** WCAG 1.4.3 exempts
  inactive components on purpose — dimming is how a control says it is inactive
  — so the greyed-out submit button on the New agent form was being filed as an
  accessibility defect. Four such lines is how a reader learns to skim a section.
